LangGraph에서 **툴(tool)** 은 단순히 함수를 등록하는 개념이 아닙니다. <br>
툴은 이제 **에이전트의 행동 단위(Behavioral Unit)** 로 동작하며,
그 입력 구조(스키마)가 곧 LLM의 **행동 가능 범위(Action Space)** 를 결정하게 됩니다!

LangChain v1에서는 `create_agent()`가 등장하면서,
툴의 스키마를 자동으로 인식·통합하는 구조로 발전했습니다. <br>
이 장에서는 LangChain v0와 v1의 차이, 그리고
v1 환경에서 스키마를 올바르게 이해하고 설계하는 방법을 배워봅시다.  
공식 마이그레이션 가이드([LangChain v1 migration](https://docs.langchain.com/oss/python/migrate/langchain-v1))에서도 강조하듯이, 이제 스키마는 단순 “입력 검증”을 넘어 에이전트의 **행동 가능 범위(action space)** 를 정의하는 핵심 요소가 되었습니다.

### ⚙️ LangChain v0 vs v1 — 스키마 개념의 진화

| 구분 | LangChain v0 (기존 방식) | LangChain v1 (create_agent 기반) |
|------|------|------|
| 에이전트 구성 | 모델과 툴을 initialize_agent 등으로 직접 연결 | create_agent(model, tools) 한 줄로 통합 |
| 스키마 정의 방식 | 수동으로 타입, 구조, 검증 정의 필요 | 함수 시그니처와 docstring에서 자동 추론 |
| 스키마의 의미 | 입력값 검증 및 포맷 지정 | LLM 행동의 인터페이스(“언제/왜 호출할지”) |
| 개발자 역할 | JSON Schema 직접 설계 | 직관적 함수명·docstring 설계 중심 |
| 결과 구조화 | 툴 결과는 문자열 중심 | ToolStrategy 등으로 구조적 출력 가능 |

요약하자면,

> 🔁 **스키마는 “검증 문서”에서 “행동 설계도”로 진화했습니다.**

이제는 스키마를 ‘작성’한다기보다,
함수 이름, 시그니처, docstring이 곧 스키마가 되는 셈입니다.

## 🧱 그럼 툴 스키마는 무엇인가요?

**“스키마(schema)”**란, **함수가 받을 수 있는 입력 구조를 정의한 약속서**입니다.
LLM은 사람이 쓰는 자연어를 이 스키마에 맞게 자동으로 채워 넣습니다.

| 구성 요소 | 설명 |
|------|------|
| 🏷️ 이름(name) | 함수(또는 툴)의 고유 식별자 |
| 🧩 인수(arguments) | 툴이 받을 수 있는 입력의 이름·타입·제약조건 |
| 💬 설명(description) | 모델이 언제·왜 이 툴을 사용해야 하는지 판단하는 힌트 |

예를 들어,
“서울의 내일 날씨 알려줘” →
모델은 `get_weather(city="서울", date="내일")` 형태로 변환합니다.
이때 `city`, `date`가 바로 툴 스키마에서 정의된 구조입니다.

## 📘 기본 스키마: 타입 힌트 기반

가장 단순한 스키마 정의 방식은 **Python 타입 힌트**를 활용하는 것입니다.
@tool 데코레이터는 함수 시그니처를 자동으로 JSON Schema 형태로 변환합니다.

```python
from langchain.tools import tool

@tool
def get_weather(city: str, date: str) -> str:
    """특정 도시와 날짜의 날씨를 반환합니다."""
    return f"{date}의 {city} 날씨는 맑음입니다."
```

```python
print(get_weather.name)         # "get_weather"
print(get_weather.description)  # "특정 도시와 날짜의 날씨를 반환합니다."
print(get_weather.args)
# {'city': {'type': 'string'}, 'date': {'type': 'string'}}
```

> 🔍 LangGraph는 함수의 시그니처와 docstring을 자동 분석해
> LLM이 이해할 수 있는 **JSON Schema 형태로 변환**합니다.

즉, 이제 별도의 스키마 클래스를 작성하지 않아도
타입 힌트와 주석만으로 충분히 “함수의 계약서”를 만들 수 있습니다.

## 🧩 복잡한 입력 구조: Pydantic 스키마 사용

입력 필드가 많거나, 특정 값만 허용해야 하는 경우엔
**Pydantic 모델**을 사용해 인수 스키마를 명확히 정의할 수 있습니다.

```python
from pydantic import BaseModel, Field
from langchain.tools import tool

class WeatherInput(BaseModel):
    city: str = Field(..., description="조회할 도시 이름 (예: 서울, 부산)")
    date: str = Field(..., description="조회할 날짜 (예: 오늘, 내일, YYYY-MM-DD 형식)")

@tool(args_schema=WeatherInput)
def get_weather(city: str, date: str) -> str:
    """도시와 날짜를 입력받아 날씨를 반환합니다."""
    return f"{date}의 {city} 날씨는 맑음입니다."
```

| 장점 | 설명 |
|------|------|
| ✅ 명확성 | 어떤 필드가 필수인지, 어떤 값이 허용되는지 명확히 표현 |
| 🧠 모델 친화적 | LLM이 필드명과 설명을 기반으로 올바른 인수를 자동 완성 |
| 🚫 오류 방지 | 잘못된 타입이나 누락된 인수 자동 검증 |
| 📦 확장 용이성 | 선택값, 기본값, 제한 조건을 쉽게 추가 가능|

### 💡 선택 인수와 기본값 지정하기

모든 인수를 필수로 둘 필요는 없습니다.
기본값을 지정하면 모델이 값을 생략해도 안전하게 작동합니다.

```python
@tool
def search_news(keyword: str, limit: int = 5) -> str:
    """뉴스 키워드 검색을 수행합니다."""
    return f"'{keyword}' 관련 최신 뉴스 {limit}개를 보여드립니다."
```

이 경우 `limit` 인수는 생략 가능하며, 기본값 5가 자동 적용됩니다.

## 🧱 스키마를 내 에이전트에 통합하기

LangChain v1에서는 `create_agent()`가 모든 툴의 스키마를 자동 통합합니다.
즉, `bind_tools()`나` initialize_agent()`를 직접 호출할 필요가 없습니다.

```python
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

agent = create_agent(
    model=ChatOpenAI(model="gpt-4o-mini"),
    tools=[get_weather, search_news],
    system_prompt="날씨나 뉴스 관련 질문에 적절한 도구를 사용하세요."
)

response = agent.invoke({
    "messages": [{"role": "user", "content": "내일 서울 날씨 어때?"}]
})
print(response["messages"][-1].content)
```

이 과정에서 `create_agent()`는 자동으로 다음을 수행합니다.

1️⃣ 모든 툴의 시그니처와 docstring을 수집
2️⃣ 내부 JSON Schema로 병합
3️⃣ 자연어 요청을 툴 인수 구조로 변환
4️⃣ 결과를 대화 컨텍스트로 반영

즉, **이제 스키마를 직접 “작성”할 필요는 줄었지만, “설계”는 여전히 필요합니다.**
왜냐하면 함수 이름과 설명이 모델의 **도구 선택 판단 로직**에 직접 영향을 미치기 때문입니다.

## 🧩 출력 구조화 (Structured Output)

LangChain v1에서는 입력뿐 아니라 출력까지 타입 세이프하게 다룰 수 있습니다.
`ToolStrategy`를 이용해 구조적 반환 형식을 지정할 수 있습니다.

```python
from langchain.agents.structured_output import ToolStrategy
from pydantic import BaseModel

class WeatherResult(BaseModel):
    temperature: float
    condition: str

agent = create_agent(
    "gpt-4o-mini",
    tools=[get_weather],
    response_format=ToolStrategy(WeatherResult)
)
```
→ 모델은 `WeatherResult(temperature=23.4, condition='sunny')` 형태로 반환합니다.
이는 LLM 출력의 신뢰성을 높이는 실무적 패턴입니다.

## 🔍 핵심 정리

### LangChain v1에서 달라진 점
| 이전 버전 | LangChain v1 이후 |
|------|------|
| 함수의 입력 형식 정의서 | LLM의 행동 가능성을 정의하는 인터페이스 |
| JSON 구조를 직접 설계 | 함수 시그니처와 설명으로 자동 생성 |
| 검증 중심 설계 | 의미 중심(semantic) 설계 |
| 입력만 다룸 | 입력 + 출력 + 호출 맥락까지 포함 |

> 🧠 결론적으로,
> “스키마를 작성하지 않아도 되지만, 스키마를 생각하며 코드를 짜야 한다.”

### 🧱 스키마 설계 가이드라인

| 원칙 | 설명 |
|------|------|
| 🎯 명확한 함수명 | 모델이 역할을 직관적으로 이해할 수 있어야 함 |
| 💬 구체적인 docstring | 언제, 왜 호출해야 하는지 서술 |
| 🧩 타입 힌트 | 가능한 모든 인수에 명시 |
| 🧠 Pydantic | 복잡 입력에 사용 (명시적 검증 및 설명 강화) |
| ⚙️ 기본값 | 불필요한 인수 생략 가능하도록 설정 |
| 🔍 테스트 | invoke()로 실제 호출 동작 확인 |

[[TIP]]
💡 **LangChain v1에서의 스키마 개념**

이제 스키마는 “입력 규칙”이 아니라 “에이전트의 행동 설계도”입니다.
좋은 이름과 명확한 설명이 곧 좋은 스키마입니다.
[[/TIP]]


✅ 이제 LangChain v1 환경에서 스키마를 ‘작성’하는 대신 ‘설계’해야 하는 이유를 이해했습니다.    <br>
