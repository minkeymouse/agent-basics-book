이 절은 3절에서 소개한 메시지 모델을 바탕으로, **실무에서 바로 쓸 수 있는 패턴 모음**을 정리한 연장선입니다. 특히 v1에서 추가된 콘텐츠 블록 구조를 어떻게 활용하면 좋을지, 멀티모달·시스템 메시지·히스토리 설계 관점에서 살펴봅니다.

## 5) 멀티모달 메시지 실무 패턴

텍스트만이 아니라 **이미지/오디오/문서**를 함께 다루면 사용자 의도를 더 정확히 파악하고, 풍부한 답변을 구성할 수 있습니다.  
v1 콘텐츠 블록 포맷을 활용해 **일관된 JSON**으로 멀티모달 메시지를 설계하는 방법을 정리합니다.

---
### 5.1) 패턴 1: 텍스트 + 이미지 (입력)
```python
# 패턴 1: 텍스트 + 이미지 (입력)
from langchain_core.messages import HumanMessage

msg1 = HumanMessage(content=[
    {"type": "text", "text": "이 사진에서 제품 모델명을 추정해줘."},
    {"type": "image", "image_url": "https://cdn.example.com/camera.jpg"}
])
```

- 텍스트 지시 → 이미지 순서로 배치하면 모델이 과업 맥락을 먼저 파악합니다.
- 내부망/보안 사유로 URL을 쓸 수 없다면 `data: base64` + `mime_type`를 사용하세요.

---

### 5.2) 패턴 2: 텍스트 + 이미지(바이너리 base64)
```python
# 패턴 2: 텍스트 + 이미지 (base64)
from langchain_core.messages import HumanMessage

msg2 = HumanMessage(content=[
    {"type": "text", "text": "이미지 내 라벨 텍스트를 읽어줘."},
    {"type": "image", "data": "<BASE64_STRING>", "mime_type": "image/png"}
])
```
- base64 사용 시 `mime_type`를 꼭 명시해 디코딩/렌더링 오류를 줄입니다.
- 대용량 base64는 메시지 크기 제한을 유발할 수 있으니 파일 크기를 사전에 줄이세요.

---

### 5.3) 패턴 3: 텍스트 + 오디오 (입력)
```python
# 패턴 3: 텍스트 + 오디오 (입력)
from langchain_core.messages import HumanMessage

msg3 = HumanMessage(content=[
    {"type": "text", "text": "이 음성의 핵심 내용을 두 줄로 요약해줘."},
    {"type": "audio", "audio_url": "https://cdn.example.com/meeting.m4a", "mime_type": "audio/m4a"}
])
```
- 오디오도 이미지와 동일한 패턴으로 **URL 또는 base64**를 제공합니다.
- 포맷별(`m4a`, `wav`, `mp3`) 지원 여부는 백엔드/모델별로 다를 수 있습니다.

---

### 5.4) 패턴 4: 텍스트 + 문서 (입력)
```python
# 패턴 4: 텍스트 + 문서 (입력)
from langchain_core.messages import HumanMessage

msg4 = HumanMessage(content=[
    {"type": "text", "text": "문서의 결론 부분을 요약해줘."},
    {"type": "document", "doc_url": "https://cdn.example.com/report.pdf", "mime_type": "application/pdf", "name": "report.pdf"}
])
```
- 문서 타입은 `document` 블록으로 전달하고, `mime_type`/`name`을 함께 두면 후처리에 유리합니다.
- 페이지 단위 분할이 필요하다면 업스트림에서 분리해 전달하는 것이 안전합니다.

---

### 5.5) 응답(출력)도 동일한 블록 구조 사용
```python
# 응답(출력)도 동일한 블록 구조 사용
from langchain_core.messages import AIMessage

msg_out = AIMessage(content=[
    {"type": "text", "text": "요약 결과를 표로 정리했습니다."},
    {"type": "image", "image_url": "https://cdn.example.com/summary_chart.png"}
])
```
- 출력 측에서도 동일한 `content` 블록 포맷을 유지하면 프런트·백엔드 렌더링이 단순해집니다.
- 이미지/문서 링크가 만료될 수 있으므로, 만료 정책과 캐시 전략을 운영 규정에 반영하세요.

---

### 5.6) 교환 포맷 템플릿(JSON)

```json
{
  "messages": [
    {
      "type": "human",
      "content": [
        {"type": "text", "text": "이 이미지의 핵심 특징을 설명해줘."},
        {"type": "image", "image_url": "https://cdn.example.com/item.png"}
      ]
    }
  ],
  "config": {
    "output_version": "v1"
  }
}
```
- `output_version: "v1"`을 쓰면 표준 블록 직렬화가 보장됩니다.
- 전송 계층(HTTP/WS)에서 본문 크기 제한을 고려해 **파일은 가급적 URL로** 전달하세요.

---

### 🔹 실무 체크리스트
- **순서가 의미**입니다: 지시 → 참고자료(이미지/오디오/문서) → 추가 지시…
- **URL 우선**, 보안/오프라인이면 **base64 + mime_type**.
- **파일 크기**: 이미지/오디오는 전송 전 리사이즈·압축으로 크기 제한을 회피.
- **형식 일관성**: 입력과 출력 모두 **동일한 블록 스키마**를 유지해 렌더링을 단순화.
- **버전 고정**: `output_version="v1"`(또는 `LC_OUTPUT_VERSION=v1`)로 직렬화 스키마 고정.
- **만료/접근 제어**: 서명 URL(짧은 TTL)·액세스 토큰·CORS를 운영 정책에 반영.

---

### 🔹 안티패턴(피해야 할 관행)
- 이미지/오디오를 **임의의 텍스트 필드**에 base64로 끼워 넣기(파싱·용량 이슈).
- `mime_type` 생략 → 디코딩 실패/불명확한 처리.
- 대용량 base64를 **여러 메시지에 중복** 삽입(과금·성능 악화).
- 입력은 블록, 출력은 문자열처럼 **포맷 혼용**(렌더러 복잡도 상승).

---

> 💡 **핵심 요약**  
> 멀티모달은 “콘텐츠 블록 리스트”로 **입출력 모두**를 표준화하면 구현과 운영이 동시에 쉬워집니다.  
> **URL 우선**, **mime_type 명시**, **버전 고정**이 안정적인 실무 기본값입니다.


## 6) 시스템 메시지 전략

**SystemMessage**는 모델의 “행동 규칙·역할·톤”을 고정하는 **정책 레이어**입니다.  
동일한 입력이라도 System이 다르면 답변의 스타일·도구 사용 여부·보안 태도가 달라집니다.

---

### 6.1) 왜 System에 두어야 하는가
| 항목 | SystemMessage | HumanMessage(요청문 내 지시) |
|---|---|---|
| **우선순위/안정성** | 상위 정책으로 일관되게 적용 | 사용자 요청에 묻혀 무시되기 쉬움 |
| **재사용성** | 에이전트/세션 간 재사용 용이 | 매번 요청문에 반복 삽입 필요 |
| **보안/규정** | 금지·제한 정책을 강제하기 적합 | 실수/편집으로 누락될 위험 |
| **톤/페르소나** | 응답 톤·형식 통일 | 요청마다 변동 가능 |

> 결론: **정책·가드레일·톤**은 System, **구체적 과업**은 Human에 두는 것이 견고합니다.

---

### 6.2) 기본 구성 템플릿

**1) 역할(Role) 정의**
- “당신은 △△ 도메인 전문 조언가입니다.”
- “항상 정확성·간결·근거 제시를 우선합니다.”

**2) 출력 형식(Format)**
- “모든 응답은 한국어로 작성.”
- “번호 목록 → 한 문장 요약 순서로.”
- “코드가 있으면 언어 표기와 주석 포함.”

**3) 품질/검증 규칙(Quality & Safety)**
- “확실치 않으면 모른다고 말하고, 확인 경로 제시.”
- “민감 정보·개인정보는 요청해도 제공하지 않음.”
- “추측 대신 가정(Assumption)을 명시.”

**4) 맥락 사용(Context Handling)**
- “최근 N개의 메시지만 사용. 불필요한 과거 히스토리 무시.”
- “제공된 표/리스트를 우선 근거로 사용.”

---

### 6.3) Do / Don’t

| Do(권장) | Don’t(지양) |
|---|---|
| 정책을 **계층적**(역할→형식→품질→안전)으로 | Human에 정책을 매번 복붙 |
| **측정 가능한 지시**(“3줄 요약”) | “최대한 자세히” 같은 모호한 지시 |
| 불확실성 **명시 + 이유** | 확인 불가 수치의 단정 |
| 출력 포맷 **고정** | 형식 옵션 과다 나열 |

---

### 6.4) 품질 체크리스트

- [ ] 한 화면에 들어오는 길이  
- [ ] 불확실성 처리 1줄 규칙  
- [ ] 금지/안전 규칙 분리 표기  
- [ ] Human 지시와 중복 없음

## 7) 메시지 히스토리와 시퀀스 설계

메시지 기반 워크플로우에서 **무엇을 얼마나, 어떤 순서로** 모델에 넘길지 결정하는 규칙은 품질·비용·일관성을 좌우합니다. 본 절은 v1 기준으로 **히스토리 윈도우**, **시퀀스 규칙**, **압축 전략**을 제시합니다.

---

### 7.1) 시퀀스 규칙(정석)

- **표준 입력 순서**: `[System, (Context...), Human, (AI, Tool, ... 반복)]`  
- **불변 정책**: `System`은 항상 가장 앞—역할/가드레일을 일관 적용.  
- **컨텍스트 우선순위**: 최신 맥락일수록 앞(또는 가까운 곳)에 배치.  
- **중간 산출물**(초안/메모/실험 로그)은 기본적으로 **포함하지 않음**. 필요한 경우 요약해 1~2줄로 대체.

---

### 7.2) 히스토리 크기 결정(윈도우링)

#### A) 고정 갯수(K messages)
- 규칙: `System 1 + 최근 K개의 Human/AI`
- 장점: 단순·예측 가능
- 단점: 토큰 폭주 시 품질 저하 가능

#### B) 토큰 예산(B tokens)
- 규칙: 상한 토큰(B) 안에서 뒤에서부터 채우기
- 장점: 비용·지연 시간 일정
- 단점: 구현 복잡도 ↑ (토큰 추산 필요)

#### C) 시간/세션 경계 기반
- 규칙: 최근 T분/세션 N개만 유지
- 장점: 장기 대화에서 ‘오래된 잡음’ 제거
- 단점: 실제 정보량 기준이 아니라 시계열 기준

> **권장 기본값**: `System + 토큰 예산 기반(예: 2–4K tokens)`에 보조로 `K=6~10개` 상한.

---

### 7.3) 포함/제외 기준(정책 표)

| 항목 | 포함 | 제외/대체 |
|---|---|---|
| System 정책 | **항상 포함** | — |
| 최근 사용자 질의 | **포함** | — |
| 최근 모델 답변(최종) | **포함** | 중간 초안은 제외 |
| 대용량 첨부(이미지/문서) | URL/핵심 메타만 | 원본 base64는 링크/요약으로 대체 |
| 도메인 지식/FAQ | “Context” 메시지로 1~2줄 요약 | 과도한 복붙 금지 |

---

### 7.4) 히스토리 압축(요약) 전략

- **헤드라인 요약**: “요약 1줄 + 결정/액션 1줄”  
- **키-팩트 추출**: 사람/지명/수치/날짜만 남김  
- **결정 로그**: “결정 A(사유), 다음 액션 B(기한)”  
- **문서/이미지**: 원문 대신 `title / url / mime_type / checksum`만 유지

> 팁: 요약을 **HumanMessage**로 넣지 말고, `System` 뒤의 **Context 블록**(text)로 넣으면 모델이 참고로 취급하기 쉽습니다.

---

### 7.5) 실무 스니펫

#### (1) 파이썬: 최근 K개 슬라이싱 + 토큰 예산 컷
```python
from typing import List
from langchain_core.messages import BaseMessage, SystemMessage

def slice_messages(messages: List[BaseMessage],
                   system: SystemMessage,
                   max_tokens: int = 3000,
                   max_k: int = 8,
                   estimate_tokens=lambda m: len(str(m.content))//4) -> List[BaseMessage]:
    # 1) 항상 System 먼저
    out = [system]
    # 2) 최신부터 역순으로 채우기
    budget = max_tokens - estimate_tokens(system)
    picked = []
    for m in reversed(messages):
        t = estimate_tokens(m)
        if t <= budget and len(picked) < max_k:
            picked.append(m)
            budget -= t
        if budget <= 0:
            break
    return out + list(reversed(picked))
```

#### (2) JSON: v1 블록 + 컨텍스트 요약 동봉
```json
{
  "messages": [
    {"role": "system", "content": [
      {"type": "text", "text": "역할: … (생략)"},
      {"type": "text", "text": "[Context] 지난 대화 요약: 주문은 A, 제약은 B, 다음 목표는 C."}
    ]},
    {"role": "user", "content": [{"type": "text", "text": "다음 단계로 어떤 문서가 필요해?"}]},
    {"role": "assistant", "content": [{"type": "text", "text": "다음 문서 목록은 …"}]}
  ],
  "config": { "output_version": "v1" }
}
```
### 7.6) 안티패턴(피하기)
-   **모든 로그/초안**을 그대로 누적 ⇒ 비용·잡음·혼동 증가
-   base64 파일을 **반복 삽입** ⇒ 토큰·전송 폭주
-   `System`을 뒤로 밀거나 누락 ⇒ 정책 무력화
-   요약을 **HumanMessage**로 주입 ⇒ 모델이 ‘사용자 지시’로 해석할 수 있음
----------

### 7.7) 체크리스트
-   입력은 항상 `[System → (Context) → Human → …]` 순서를 유지한다.
-   토큰 예산/개수/시간 중 **하나 이상**으로 윈도우를 제한한다.
-   대용량은 **URL/메타**로 대체하고, base64는 예외적 상황에서만 쓴다.
-   중간 산출물은 **요약 1~2줄**로 압축해 Context로 편입한다.
-   `output_version="v1"` 설정을 고정한다(직렬화 일관성).
> **핵심 요약**: 히스토리는 **짧고 맥락 충실하게**, 시퀀스는 **System 선행**, 대용량은 **요약/메타**로.  
> 품질·비용·지연 시간을 동시에 관리하려면 **토큰 예산 + K개 상한**이 가장 실용적입니다.
