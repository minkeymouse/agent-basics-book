## 도대체 에이전트가 뭔데?

그동안 AI 에이전트의 정의가 뭔지 명확한 합의가 이루어지지 않아 혼란이 많았습니다. 굳이 정의를 내리지 않고 'LLM을 기반으로 하여 도구를 호출하며 뭔가를 해주는 것'을 두루뭉실하게 '에이전트'라 관행적으로 불러왔기도 합니다. 사실 이같은 논쟁은 최근의 일이 아닙니다. 자세한 내용은 링크 [에이전트가 뭔데?](https://simonwillison.net/2025/Sep/18/agents/) 를 참고하면 되겠습니다.

2025년 7월, OpenAI의 CEO 샘 알트먼은 에이전트를 '사용자를 위해 독립적으로 일하는 AI시스템'으로 정의했습니다. 랭그래프를 활용할때는 앞으로 좀더 명확한 정의를 사용하겠습니다.

[[TIP("정의")]]
LLM과 상호작용 하며 **루프** 하에서 **목표**를 위해 **도구**를 호출하는 최소한의 단위
[[/TIP]]

이 정의는 LangChain/LangGraph v1 문서에서 이야기하는 에이전트 개념과도 잘 맞습니다. 공식 문서는 에이전트를 “LLM + 도구 + 메모리 + 정책”으로 이루어진 시스템으로 보고, 이 조합이 루프를 돌며 사용자를 대신해 일을 수행한다고 설명합니다. 우리는 이를 조금 더 직관적인 말로 정리해 “목표를 향해 루프를 돌며 도구를 쓰는 최소 단위”라고 부르겠습니다.

단순히 위와 같이 에이전트를 정의하는 쪽으로 커뮤니티의 합의가 이루어지고 있다는 점을 떠나, 이렇게 정의하는 것에는 세 가지 이점이 있습니다.

먼저 **루프**를 기준으로 시스템을 정의하기 때문에, 메인 에이전트와 서브 에이전트의 구분이 가능해 집니다. 간단한 자료조사 에이전트를 생각해 본다면, 메인 에이전트가 어떤 자료들을 찾을지, 어떻게 취합할지 정의하면 서브 에이전트가 자료를 취합하고 조사하여 보고서를 제출합니다. 이 경우 랭그래프에서는 메인 에이전트의 루프 내에서 서브 에이전트의 루프가 실행되는데, **루프**를 기준으로 정의함으로써 명확하게 구분할 수 있게 됩니다.

두번째 이점은 **목표**를 기준으로 에이전트를 정의하여 언제까지 시스템이 실행될지, 언제 멈출지 구분할 수 있습니다. 목표를 이루지 못했거나, 사용자의 피드백이 필요한 경우 루프를 중단함으로써 에이전트가 실행되는 단위를 세분화하여 조절할 수 있습니다.

마지막으로 **도구**는 에이전트가 단순한 LLM을 넘어 실무에 활용될 수 있는 최소 단위 입니다. 인터넷을 찾아보고, 문서를 작성하고, 파일을 수정하는 등의 작업이 가능해야 이를 '에이전트'라고 부를 수 있습니다. 도구 호출이 없다면 단순 대형언어모델에 불과하기 때문에 이 역시 에이전트를 정의하기 위해 필요한 최소 단위로 생각할 수 있겠습니다.

## 에이전트 vs 랭그래프 vs 랭체인 — 차이 정리 (0장에 추가하면 좋을것 같음)

### 1) 핵심 정의
- **에이전트(Agent, 개념)**  
  LLM이 *목표*를 달성하기 위해 **루프**를 돌며 필요 시 **도구**를 호출하는 실행 단위.  
  ↳ 관점: “무엇을 하느냐(행동 패턴)”

- **랭그래프(LangGraph, 오케스트레이션 엔진)**  
  에이전트의 **루프/분기/상태**를 **노드와 엣지**로 **명시적** 모델링하고, **체크포인트·재개·휴먼 승인** 같은 운영 기능을 제공.  
  ↳ 관점: “어떻게 안전하게 돌리고 관찰·재현하느냐(런타임/워크플로)”

- **랭체인(LangChain, LLM 앱 프레임워크)**  
  프롬프트·체인·에이전트 추상화와 수많은 통합(모델·DB·툴)을 제공하여 **빠르게 조립**하고 실험하기 좋음.  
  ↳ 관점: “무엇으로 빠르게 만들고 연결하느냐(SDK/컴포넌트)”

---

| 구분 | 에이전트(개념) | 랭그래프(LangGraph) | 랭체인(LangChain) |
|---|---|---|---|
| 정체성 | 행동 패턴(루프·목표·도구) | 오케스트레이션/런타임 | 프레임워크/SDK |
| 제어 흐름 | 추상적 개념 | **명시적 그래프 분기** | 비교적 **암시적 체인/에이전트** |
| 상태 관리 | 필요(개념상) | **단일 State + 체크포인트** | 외부 저장/핸들러 조합 |
| 실패/재시도 | 필요(개념상) | **엣지로 실패·폴백·승인** | 핸들러/콜백/재시도 래퍼 |
| 장기 실행 | 개념상 가능 | **중단·재개·휴먼 인터럽트** | 가능하나 부가구성 필요 |
| 관찰/재현성 | 개념상 중요 | **노드 I/O 추적·재현 용이** | 로깅·트레이싱 추가 필요 |
| 생산 단계 적합 | 조건부 | **프로덕션 에이전트** | **PoC/프로토타입** 강점 |
| 학습 곡선 | – | 그래프·상태 설계가 필요 | 낮음(빠른 조립) |
| 상호 보완 | – | 노드 내부에 랭체인 사용 가능 | 랭그래프 내에서 재사용 가능 |

---

### 3) 역할/스코프 구분
- **에이전트**는 “행동 규약(Observe–Think–Act 루프 + 종료 조건 + 도구 사용)”을 말합니다.  
- **랭그래프**는 그 규약을 **운영 가능한 형태**(그래프)로 **고정**하고 **관찰·재현**을 쉽게 해 줍니다.  
- **랭체인**은 LLM 호출, RAG, 툴 통합 등을 **신속히 조립**하도록 돕고, 필요 시 이 컴포넌트를 **랭그래프의 노드 내부**에서 활용할 수 있습니다.

---

### 4) 언제 무엇을 쓸까 (체크리스트)

- **빠른 데모/검증(PoC)**, 단일 흐름, 연결 작업이 많다 → **랭체인**
- **분기/루프가 많다**, 실패·재시도·폴백·승인 등 **명시적 제어**가 필요하다 → **랭그래프**
- **감사/로그/재현성(금융·의료·기업 내부 규정)**이 중요하다 → **랭그래프**
- **서브에이전트·병렬 브랜치**가 여럿이다 → **랭그래프**
- **혼합 전략**: “랭체인으로 빠르게 만들고 → 규모·안정성 요구 시 랭그래프로 이관(노드 내부에서 랭체인 재사용)”
