## 1) 왜 ‘메시지’인가

LLM과 대화할 때 우리는 흔히 “문자열(prompt)” 하나만 전달하는 방식을 떠올립니다.  
하지만 실제로는 한 줄짜리 문자열로는 **다중 턴 대화, 툴 호출, 멀티모달 입력** 등을 제대로 표현하기 어렵습니다.  
이 한계를 해결하기 위해 LangChain과 LangGraph는 **‘메시지(Message)’를 표준 단위**로 삼습니다.  
특히 v1에서는 메시지에 역할(Role)과 콘텐츠 블록(content blocks)을 명시적으로 담아, 에이전트의 상태와 도구 호출 내역을 한눈에 추적할 수 있도록 설계했습니다.

---

### 문자열 vs 메시지

| 구분 | 문자열 입력 | 메시지 입력 |
|------|--------------|--------------|
| 입력 구조 | 단일 문자열 | `SystemMessage`, `HumanMessage`, `AIMessage` 등 객체 리스트 |
| 대화 맥락 | 유지 어려움 | 이전 턴까지의 메시지들을 모두 포함 |
| 툴 호출 | 문자열 파싱으로 복잡 | `AIMessage.tool_calls` 등 구조화된 필드로 처리 |
| 멀티모달 | 직접 불가 | 이미지, 오디오 등 다양한 콘텐츠 블록 포함 가능 |
| 상태 관리 | 모델 외부에서 따로 추적 | `state.messages`에 그대로 저장·재사용 가능 |

이처럼 메시지는 단순한 문자열을 넘어,  **에이전트의 “생각–행동–관찰” 과정 전체를 기록하는 데이터 단위**로 작동합니다.

---


###  에이전트 내부에서의 메시지 흐름

LangGraph에서 오가는 모든 데이터는 결국 **메시지 리스트(Message list)** 형태로 구성됩니다.

```python
[
    SystemMessage(content="당신은 친절한 여행 도우미입니다."),
    HumanMessage(content="파리 여행 계획을 세워줘."),
    AIMessage(content="3일간의 파리 여행 일정을 제안드릴게요. 첫째 날은 에펠탑부터 시작해볼까요?")
]
```

---

### 핵심 정리

- 단순 문자열은 “한 턴(one shot)”에만 적합하다.  
- **LangChain/LangGraph는 구조화된 메시지 리스트를 표준화**하여 멀티턴·멀티모달·툴콜을 모두 일관성 있게 다룬다.  
- 메시지는 **상태(State)** 와 **대화 히스토리**를 연결하는 핵심 단위다.  
- Agent Builder에서도 모든 노드 간 주고받는 데이터는 결국 “메시지 리스트”다.

---

> 💡 **한 문장 요약**  
> “에이전트는 문자열이 아니라 메시지로 생각한다.”


##  2) 기본 메시지 타입

LangChain과 LangGraph에서 메시지는 단순한 텍스트가 아니라 **역할(Role)** 이 명확히 구분된 객체로 표현됩니다.  
이 네 가지 메시지 타입이 모든 대화의 기본 단위를 이룹니다.

---

### 주요 메시지 타입

| 타입 | 설명 | 사용 시점 |
|------|------|------------|
| **SystemMessage** | 모델에게 규칙·역할·지침을 전달합니다. | 대화의 시작, 혹은 정책 변경 시 |
| **HumanMessage** | 사용자의 실제 입력을 전달합니다. | 매 턴의 사용자 요청 시 |
| **AIMessage** | 모델의 응답을 나타냅니다. 툴 호출 정보도 포함될 수 있습니다. | 모델이 생각(Reason)·행동(Action)을 출력할 때 |
| **ToolMessage** | 툴 실행 결과를 모델로 다시 전달합니다. | AIMessage가 툴을 호출한 직후 |

---


```python
[
    SystemMessage(content="툴이 있으면 반드시 사용해라."),
    HumanMessage(content="서울 날씨 알려줘"),
    AIMessage(tool_calls=[{"name": "get_weather", "args": {"location": "서울"}}]),
    ToolMessage(content="서울의 현재 기온은 18도입니다."),
    AIMessage(content="서울의 현재 기온은 18도입니다 ☀️")
]
```
이 예시는 한 번의 대화 턴 안에서 **System → Human → AI → Tool → AI** 흐름이 모두 이루어지는 전형적인 구조입니다.  
에이전트 그래프에서는 이 메시지들이 순서대로 `state.messages`에 저장되고,  
다음 노드(agent)가 이 리스트를 그대로 모델 입력으로 사용합니다.

---

### 메시지 타입별 요약

- **SystemMessage** : 모델의 행동 규칙을 고정 (예: “항상 한국어로만 답해.”)  
- **HumanMessage** : 사용자로부터 들어오는 실제 요청  
- **AIMessage** : 모델이 생성한 응답 또는 툴 호출 명령  
- **ToolMessage** : 툴 실행 결과를 다시 모델에게 전달  

---

> 💡 **핵심 요약**  
> LangChain/LangGraph의 모든 대화는 이 네 가지 메시지 타입으로 표현된다.  
> 문자열이 아니라 **“구조화된 역할 메시지들”**이 쌓이면서 에이전트의 상태(State)가 유지된다.


## 3. 메시지 속성(Attributes) 빠르게 훑기

메시지는 단순 텍스트가 아니라 **역할(Role) + 콘텐츠(Content) + 메타데이터(Metadata)**를 담는 객체입니다.
아래 표는 실무에서 가장 자주 쓰는 공통 속성을 요약한 것입니다.

> 기본 메시지 타입: `SystemMessage`, `HumanMessage`, `AIMessage`, `ToolMessage`  
> (자세한 타입 설명은 3.2 참고)

---

### 🔹 핵심 속성 요약

| 속성 | 유형 | 설명 | 비고 |
|---|---|---|---|
| `content` | str \| list | 메시지 본문. v1에서는 **콘텐츠 블록 리스트** 권장 | 텍스트만 있으면 str도 가능 |
| `content_blocks` | list | 표준화된 **콘텐츠 블록**(텍스트/이미지/오디오/문서/추론 등) | 멀티모달·표준 직렬화에 유리 |
| `tool_calls` | list | `AIMessage`가 지시한 **툴 호출 목록** | 각 item은 `name`, `args` 포함 |
| `id` | str | 메시지 식별자 | 로깅·추적에 유용 |
| `usage_metadata` | dict | 토큰 사용량 등 과금 관련 정보 | 모델/프로바이더별 제공 여부 상이 |
| `response_metadata` | dict | 응답에 대한 부가정보(모델명 등) | 디버깅·모니터링에 활용 |
| `type` | str | 메시지 타입 식별자(예: `ai`, `human`) | 주로 내부적으로 사용 |

- `content` vs `content_blocks`  
  - 단순 텍스트만 다루면 `content: str`로 충분합니다.  
  - 멀티모달·툴콜·추론 블록 등 **구조화된 표준 포맷**을 쓰려면 `content_blocks: list`를 권장합니다. :contentReference[oaicite:0]{index=0}

---

#### 🔹 예시: 텍스트 중심

```python
from langchain_core.messages import HumanMessage, AIMessage

msgs = [
    HumanMessage(content="안녕하세요, 오늘 일정 요약해줘."),
    AIMessage(
        content="다음은 오늘 일정입니다.\n1) 10:00 팀 미팅\n2) 14:00 코드 리뷰"
    )
]
```
- 텍스트만 있다면 `content`를 문자열로 써도 충분합니다.

#### 🔹  표준 콘텐츠 블록 예시: 멀티모달/구조화
```python
from langchain_core.messages import HumanMessage

msg = HumanMessage(
    content=[
        {"type": "text", "text": "이 사진에서 핵심 사물을 설명해줘."},
        {"type": "image", "image_url": "https://example.com/photo.png"}
    ]
)
```
- 하나의 메시지에 **여러 블록**을 넣어 멀티모달 입력을 구성합니다.
-   표준 블록은 교차-프로바이더 호환성(표준 직렬화)에 유리합니다.

####  🔹 툴 호출 메타데이터: `AIMessage.tool_calls`
```python
from langchain_core.messages import AIMessage

ai = AIMessage(
    content="날씨 정보를 조회합니다.",
    tool_calls=[{"name": "get_weather", "args": {"location": "Seoul"}}]
)
```
- 모델이 툴을 쓰려면 **AIMessage가 툴콜을 선언**하고, 이어지는 `ToolMessage`로 결과를 받습니다 (이후 챕터에서 설명이 있음 - 어떻게 할지 논의 필요.)

####   🔹 사용량/응답 메타데이터: `usage_metadata`, `response_metadata`
```python
from langchain_core.messages import AIMessage

ai = AIMessage(
    content="완료했습니다.",
    usage_metadata={"input_tokens": 512, "output_tokens": 128},
    response_metadata={"model_name": "gpt-4o-mini"}
)
```
- 토큰/비용 추정, 모델명·버전 파악, 디버깅에 유용합니다(제공 범위는 백엔드별 상이).

####  🔹 스트리밍과 청크: `AIMessageChunk`
스트리밍 시에는 완성된 `AIMessage` 대신 **`AIMessageChunk` 조각**이 순차적으로 도착합니다.  
여러 청크를 **덧셈(+) 연산**으로 합쳐 최종 메시지를 만들 수 있습니다.


## 4) 메시지 콘텐츠 모델(콘텐츠 블록)

v1 기준에서 메시지의 `content`는 **문자열**뿐 아니라 **콘텐츠 블록 리스트**로 표현할 수 있습니다.  
이 블록들은 텍스트, 추론(Reasoning), 이미지, 오디오, 문서 등 다양한 타입을 표준화된 필드로 담습니다.  
즉, 하나의 메시지에 여러 매체를 **순서 있는 리스트**로 결합할 수 있습니다.
- **일관성**: 텍스트/이미지/오디오를 동일한 포맷으로 전달  
- **상호운용성**: 프론트·백엔드 간 JSON 교환이 쉬움  
- **미래지향성**: 새로운 블록 타입을 추가해도 공용 인터페이스 유지

---

### 기본 형태

단일 문자열(레거시/간단):
```python
AIMessage(content="하루 일정을 요약해드릴게요.")
```
콘텐츠 블록 리스트(권장):
```python
AIMessage(content=[
  {"type": "text", "text": "하루 일정을 요약해드릴게요."}
])
```
###  표준 블록 타입

| 타입 | 핵심 필드 | 용도/설명 |
|---|---|---|
| `text` | `text: str` | 일반 텍스트 본문 |
| `reasoning` | `text: str`, `level: "low" / "medium" / "high"` *(선택)* | 모델의 추론/근거를 구조화해 전달 |
| `image` | `image_url: str` **또는** `data: base64`, `mime_type` | 이미지 입력/출력(URL 또는 바이트) |
| `audio` | `audio_url: str` **또는** `data: base64`, `mime_type` | 음성 입력/출력 |
| `document` | `doc_url` **또는** `data: base64`, `mime_type`, `name` | PDF/문서 등 파일형 콘텐츠 |

> 구현체/프로바이더에 따라 지원 범위와 세부 필드는 다를 수 있습니다.

#### 예시 1: 텍스트 + 이미지
```python
from langchain_core.messages import HumanMessage

msg = HumanMessage(content=[
  {"type": "text", "text": "이 사진의 핵심 사물을 설명해줘."},
  {"type": "image", "image_url": "https://example.com/photo.png"}
])
```

#### 예시 2: 텍스트 + 추론(Reasoning) + 결과 텍스트
```python
from langchain_core.messages import AIMessage

msg = AIMessage(content=[
  {"type": "reasoning", "text": "요청 의도를 파악하고 3개 항목으로 요약하자."},
  {"type": "text", "text": "요약: 1) 일정 파악 2) 우선순위 3) 준비물 체크"}
])
```

#### 예시 3: 오디오 입력
```python
from langchain_core.messages import HumanMessage

msg = HumanMessage(content=[
  {"type": "text", "text": "이 음성의 핵심 내용을 한 줄로 요약해줘."},
  {"type": "audio", "audio_url": "https://example.com/meeting.m4a", "mime_type": "audio/m4a"}
])
```
---

### 직렬화/버전 설정 팁

- **v1 직렬화 사용**: 환경변수 `LC_OUTPUT_VERSION=v1` *(또는 클라이언트 옵션에서 `output_version="v1"`)*  
- **효과**: 모든 메시지가 **표준 블록 포맷**으로 일관되게 직렬화되어
  - 멀티모달 데이터 교환이 쉬워지고
  - 프로바이더별 상이한 응답 형식을 상단에서 통일

---

### 설계 체크리스트

- 블록 **순서**는 의미를 가집니다 *(예: 사용자 지시 → 참고 이미지 → 추가 지시 …)*.
- **URL vs base64**: 실무에서는 **URL 우선**, 보안/오프라인이면 base64 고려.
- `mime_type`는 가급적 명시하여 **디코딩·렌더링 오류**를 줄이기.
- 텍스트만이라도 **블록 리스트**로 시작하면, 멀티모달 **확장**이 수월합니다.

>💡 **핵심 요약**  
>메시지의 `content`는 v1에서 **콘텐츠 블록 리스트**가 표준이며,  
텍스트·추론·이미지·오디오·문서를 **한 메시지 안에서 일관된 JSON**으로 표현할 수 있습니다.

## 5) 멀티모달 메시지 실무 패턴

텍스트만이 아니라 **이미지/오디오/문서**를 함께 다루면 사용자 의도를 더 정확히 파악하고, 풍부한 답변을 구성할 수 있습니다.  
v1 콘텐츠 블록 포맷을 활용해 **일관된 JSON**으로 멀티모달 메시지를 설계하는 방법을 정리합니다.

---


### 패턴 1: 텍스트 + 이미지 (입력)
```python
# 패턴 1: 텍스트 + 이미지 (입력)
from langchain_core.messages import HumanMessage

msg1 = HumanMessage(content=[
    {"type": "text", "text": "이 사진에서 제품 모델명을 추정해줘."},
    {"type": "image", "image_url": "https://cdn.example.com/camera.jpg"}
])
```

- 텍스트 지시 → 이미지 순서로 배치하면 모델이 과업 맥락을 먼저 파악합니다.
- 내부망/보안 사유로 URL을 쓸 수 없다면 `data: base64` + `mime_type`를 사용하세요.

---

### 패턴 2: 텍스트 + 이미지(바이너리 base64)
```python
# 패턴 2: 텍스트 + 이미지 (base64)
from langchain_core.messages import HumanMessage

msg2 = HumanMessage(content=[
    {"type": "text", "text": "이미지 내 라벨 텍스트를 읽어줘."},
    {"type": "image", "data": "<BASE64_STRING>", "mime_type": "image/png"}
])
```
- base64 사용 시 `mime_type`를 꼭 명시해 디코딩/렌더링 오류를 줄입니다.
- 대용량 base64는 메시지 크기 제한을 유발할 수 있으니 파일 크기를 사전에 줄이세요.

---

### 패턴 3: 텍스트 + 오디오 (입력)
```python
# 패턴 3: 텍스트 + 오디오 (입력)
from langchain_core.messages import HumanMessage

msg3 = HumanMessage(content=[
    {"type": "text", "text": "이 음성의 핵심 내용을 두 줄로 요약해줘."},
    {"type": "audio", "audio_url": "https://cdn.example.com/meeting.m4a", "mime_type": "audio/m4a"}
])
```
- 오디오도 이미지와 동일한 패턴으로 **URL 또는 base64**를 제공합니다.
- 포맷별(`m4a`, `wav`, `mp3`) 지원 여부는 백엔드/모델별로 다를 수 있습니다.

---

### 패턴 4: 텍스트 + 문서 (입력)
```python
# 패턴 4: 텍스트 + 문서 (입력)
from langchain_core.messages import HumanMessage

msg4 = HumanMessage(content=[
    {"type": "text", "text": "문서의 결론 부분을 요약해줘."},
    {"type": "document", "doc_url": "https://cdn.example.com/report.pdf", "mime_type": "application/pdf", "name": "report.pdf"}
])
```
- 문서 타입은 `document` 블록으로 전달하고, `mime_type`/`name`을 함께 두면 후처리에 유리합니다.
- 페이지 단위 분할이 필요하다면 업스트림에서 분리해 전달하는 것이 안전합니다.

---

### 응답(출력)도 동일한 블록 구조 사용

```python
msg_out = AIMessage(content=[
    {"type": "text", "text": "요약 결과를 표로 정리했습니다."},

```
- 출력 측에서도 동일한 `content` 블록 포맷을 유지하면 프런트·백엔드 렌더링이 단순해집니다.
- 이미지/문서 링크가 만료될 수 있으므로, 만료 정책과 캐시 전략을 운영 규정에 반영하세요.

### 교환 포맷 템플릿(JSON)

```json
{

    {
      "type": "human",
      "content": [
        {"type": "text", "text": "이 이미지의 핵심 특징을 설명해줘."},

```
- `output_version: "v1"`을 쓰면 표준 블록 직렬화가 보장됩니다.
- 전송 계층(HTTP/WS)에서 본문 크기 제한을 고려해 **파일은 가급적 URL로** 전달하세요.

---

### 🔹 실무 체크리스트
- **순서가 의미**입니다: 지시 → 참고자료(이미지/오디오/문서) → 추가 지시…
- **URL 우선**, 보안/오프라인이면 **base64 + mime_type**.
- **파일 크기**: 이미지/오디오는 전송 전 리사이즈·압축으로 크기 제한을 회피.
- **형식 일관성**: 입력과 출력 모두 **동일한 블록 스키마**를 유지해 렌더링을 단순화.
- **버전 고정**: `output_version="v1"`(또는 `LC_OUTPUT_VERSION=v1`)로 직렬화 스키마 고정.
- **만료/접근 제어**: 서명 URL(짧은 TTL)·액세스 토큰·CORS를 운영 정책에 반영.

---

### 🔹 안티패턴(피해야 할 관행)
- 이미지/오디오를 **임의의 텍스트 필드**에 base64로 끼워 넣기(파싱·용량 이슈).
- `mime_type` 생략 → 디코딩 실패/불명확한 처리.
- 대용량 base64를 **여러 메시지에 중복** 삽입(과금·성능 악화).
- 입력은 블록, 출력은 문자열처럼 **포맷 혼용**(렌더러 복잡도 상승).

---

> 💡 **핵심 요약**  
> 멀티모달은 “콘텐츠 블록 리스트”로 **입출력 모두**를 표준화하면 구현과 운영이 동시에 쉬워집니다.  
> **URL 우선**, **mime_type 명시**, **버전 고정**이 안정적인 실무 기본값입니다.


## 6) 시스템 메시지 전략

**SystemMessage**는 모델의 “행동 규칙·역할·톤”을 고정하는 **정책 레이어**입니다.  
동일한 입력이라도 System이 다르면 답변의 스타일·도구 사용 여부·보안 태도가 달라집니다.

---

### 왜 System에 두어야 하는가
| 항목 | SystemMessage | HumanMessage(요청문 내 지시) |
|---|---|---|
| **우선순위/안정성** | 상위 정책으로 일관되게 적용 | 사용자 요청에 묻혀 무시되기 쉬움 |
| **재사용성** | 에이전트/세션 간 재사용 용이 | 매번 요청문에 반복 삽입 필요 |
| **보안/규정** | 금지·제한 정책을 강제하기 적합 | 실수/편집으로 누락될 위험 |
| **톤/페르소나** | 응답 톤·형식 통일 | 요청마다 변동 가능 |

> 결론: **정책·가드레일·톤**은 System, **구체적 과업**은 Human에 두는 것이 견고합니다.

---

### 기본 구성 템플릿

**1) 역할(Role) 정의**
- “당신은 △△ 도메인 전문 조언가입니다.”
- “항상 정확성·간결·근거 제시를 우선합니다.”

**2) 출력 형식(Format)**
- “모든 응답은 한국어로 작성.”
- “번호 목록 → 한 문장 요약 순서로.”
- “코드가 있으면 언어 표기와 주석 포함.”

**3) 품질/검증 규칙(Quality & Safety)**
- “확실치 않으면 모른다고 말하고, 확인 경로 제시.”
- “민감 정보·개인정보는 요청해도 제공하지 않음.”
- “추측 대신 가정(Assumption)을 명시.”

**4) 맥락 사용(Context Handling)**
- “최근 N개의 메시지만 사용. 불필요한 과거 히스토리 무시.”
- “제공된 표/리스트를 우선 근거로 사용.”

---

###  Do / Don’t

| Do(권장) | Don’t(지양) |
|---|---|
| 정책을 **계층적**(역할→형식→품질→안전)으로 | Human에 정책을 매번 복붙 |
| **측정 가능한 지시**(“3줄 요약”) | “최대한 자세히” 같은 모호한 지시 |
| 불확실성 **명시 + 이유** | 확인 불가 수치의 단정 |
| 출력 포맷 **고정** | 형식 옵션 과다 나열 |

---

### 품질 체크리스트

- [ ] 한 화면에 들어오는 길이  
- [ ] 불확실성 처리 1줄 규칙  
- [ ] 금지/안전 규칙 분리 표기  
- [ ] Human 지시와 중복 없음

## 7) 메시지 히스토리와 시퀀스 설계

메시지 기반 워크플로우에서 **무엇을 얼마나, 어떤 순서로** 모델에 넘길지 결정하는 규칙은 품질·비용·일관성을 좌우합니다. 본 절은 v1 기준으로 **히스토리 윈도우**, **시퀀스 규칙**, **압축 전략**을 제시합니다.

---

### 시퀀스 규칙(정석)

- **표준 입력 순서**: `[System, (Context...), Human, (AI, Tool, ... 반복)]`  
- **불변 정책**: `System`은 항상 가장 앞—역할/가드레일을 일관 적용.  
- **컨텍스트 우선순위**: 최신 맥락일수록 앞(또는 가까운 곳)에 배치.  
- **중간 산출물**(초안/메모/실험 로그)은 기본적으로 **포함하지 않음**. 필요한 경우 요약해 1~2줄로 대체.

---

### 히스토리 크기 결정(윈도우링)

#### A) 고정 갯수(K messages)
- 규칙: `System 1 + 최근 K개의 Human/AI`
- 장점: 단순·예측 가능
- 단점: 토큰 폭주 시 품질 저하 가능

#### B) 토큰 예산(B tokens)
- 규칙: 상한 토큰(B) 안에서 뒤에서부터 채우기
- 장점: 비용·지연 시간 일정
- 단점: 구현 복잡도 ↑ (토큰 추산 필요)

#### C) 시간/세션 경계 기반
- 규칙: 최근 T분/세션 N개만 유지
- 장점: 장기 대화에서 ‘오래된 잡음’ 제거
- 단점: 실제 정보량 기준이 아니라 시계열 기준

> **권장 기본값**: `System + 토큰 예산 기반(예: 2–4K tokens)`에 보조로 `K=6~10개` 상한.

---

### 포함/제외 기준(정책 표)

| 항목 | 포함 | 제외/대체 |
|---|---|---|
| System 정책 | **항상 포함** | — |
| 최근 사용자 질의 | **포함** | — |
| 최근 모델 답변(최종) | **포함** | 중간 초안은 제외 |
| 대용량 첨부(이미지/문서) | URL/핵심 메타만 | 원본 base64는 링크/요약으로 대체 |
| 도메인 지식/FAQ | “Context” 메시지로 1~2줄 요약 | 과도한 복붙 금지 |

---

### 히스토리 압축(요약) 전략

- **헤드라인 요약**: “요약 1줄 + 결정/액션 1줄”  
- **키-팩트 추출**: 사람/지명/수치/날짜만 남김  
- **결정 로그**: “결정 A(사유), 다음 액션 B(기한)”  
- **문서/이미지**: 원문 대신 `title / url / mime_type / checksum`만 유지

> 팁: 요약을 **HumanMessage**로 넣지 말고, `System` 뒤의 **Context 블록**(text)로 넣으면 모델이 참고로 취급하기 쉽습니다.

---

### 실무 스니펫

#### (1) 파이썬: 최근 K개 슬라이싱 + 토큰 예산 컷
```python
from typing import List
from langchain_core.messages import BaseMessage, SystemMessage

def slice_messages(messages: List[BaseMessage],
                   system: SystemMessage,
                   max_tokens: int = 3000,
                   max_k: int = 8,
                   estimate_tokens=lambda m: len(str(m.content))//4) -> List[BaseMessage]:
    # 1) 항상 System 먼저
    out = [system]
    # 2) 최신부터 역순으로 채우기
    budget = max_tokens - estimate_tokens(system)
    picked = []
    for m in reversed(messages):
        t = estimate_tokens(m)
        if t <= budget and len(picked) < max_k:
            picked.append(m)
            budget -= t
        if budget <= 0:
            break
    return out + list(reversed(picked))
```

#### (2) JSON: v1 블록 + 컨텍스트 요약 동봉
```json
{
  "messages": [
    {"role": "system", "content": [
      {"type": "text", "text": "역할: … (생략)"},
      {"type": "text", "text": "[Context] 지난 대화 요약: 주문은 A, 제약은 B, 다음 목표는 C."}
    ]},
    {"role": "user", "content": [{"type": "text", "text": "다음 단계로 어떤 문서가 필요해?"}]},
    {"role": "assistant", "content": [{"type": "text", "text": "다음 문서 목록은 …"}]}
  ],
  "config": { "output_version": "v1" }
}
```
### 안티패턴(피하기)
-   **모든 로그/초안**을 그대로 누적 ⇒ 비용·잡음·혼동 증가
-   base64 파일을 **반복 삽입** ⇒ 토큰·전송 폭주
-   `System`을 뒤로 밀거나 누락 ⇒ 정책 무력화
-   요약을 **HumanMessage**로 주입 ⇒ 모델이 ‘사용자 지시’로 해석할 수 있음
----------

### 체크리스트
-   입력은 항상 `[System → (Context) → Human → …]` 순서를 유지한다.
-   토큰 예산/개수/시간 중 **하나 이상**으로 윈도우를 제한한다.
-   대용량은 **URL/메타**로 대체하고, base64는 예외적 상황에서만 쓴다.
-   중간 산출물은 **요약 1~2줄**로 압축해 Context로 편입한다.
-   `output_version="v1"` 설정을 고정한다(직렬화 일관성).
> **핵심 요약**: 히스토리는 **짧고 맥락 충실하게**, 시퀀스는 **System 선행**, 대용량은 **요약/메타**로.  
> 품질·비용·지연 시간을 동시에 관리하려면 **토큰 예산 + K개 상한**이 가장 실용적입니다.
