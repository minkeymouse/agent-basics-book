**스트리밍**을 통해서 에이전트의 실행과정을 추적하는 법을 배웠으니, 이제 본격적으로 에이전트를 제어해 보겠습니다. 에이전트의 행동은 주로 **도구 호출**을 통해 이루어지기 때문에 호출 과정을 제어하는 것이 중요합니다. 이번 섹션에서는 제어를 위한 핵심 요소인 **미들웨어(middleware)** 에 대해 알아보겠습니다.

## 🧠 어떻게 에이전트의 행동을 제어할 수 있을까요?

**미들웨어**란 말그대로 중간중간에서 에이전트의 행동을 제어할 수 있게 해주는 프로그램 입니다. 아래 그림에서 주황색으로 표시된 부분들이 에이전트 워크플로우에서 각 미들웨어가 동작하는 포인트 입니다. 미들웨어는 랭체인에 정의되어 있는 것들을 불러와도 좋고, 에이전트에 맞게 직접 정의할 수도 있습니다.

![middleware1](https://wikidocs.net/images/page/299480/middleware.png)

### 문제점

앞서 정의한 아기 에이전트는 **잘못된 인자와 함께 도구를 반복적으로 호출**하거나, 간혹 **불필요한 도구를 호출**하는 등의 오류가 있었습니다. 이 때문에 루프가 지연되는 일도 빈번했습니다. 중간에 멈출 수 있도록, 정해진 만큼만 루프가 실행되도록 제어하려면 어떻게 해야 할까요?

## 기본 미들웨어

이러한 문제를 해결하기 위해 **미들웨어**가 활용됩니다. 먼저 모델과 도구의 호출을 제어하는 랭체인 기본 미들웨어로 에이전트를 통제해 보겠습니다.

```python
from langchain.agents.middleware import ModelCallLimitMiddleware, ToolCallLimitMiddleware, ToolRetryMiddleware

model_call_limit_middleware = ModelCallLimitMiddleware(run_limit=4, exit_behavior="end")
global_tool_call_limit = ToolCallLimitMiddleware(run_limit=2, exit_behavior="end")
poo_tool_call_limit = ToolCallLimitMiddleware(tool_name="poo",run_limit=1, exit_behavior="end")
tool_retry_middleware = ToolRetryMiddleware(max_retries=3)
```

**기본 미들웨어**는 위와 같이 불러온 다음 인자를 알맞게 넣어주기만 하면 됩니다! 이제 시스템 프롬프트를 정의하고, 에이전트를 생성해 보겠습니다.

```python
my_system_prompt = f"""
너는 아기 에이전트야. 너의 지금 기분은 {current_mood}야. 이 값에 따라 아래 상태 규칙을 엄격히 따르며 응답해. 
- happy: 도구 호출 금지. 아기가 기분이 좋은 것 처럼 짧은 의성어로 즉시 대답해.
- hungry: 반드시 eat 도구를 1회 호출. 
    • food.txt가 있어 내용을 읽으면(도구가 텍스트 반환) 내부 상태를 happy로 전환했다고 가정하고, 짧은 의성어로 마무리.
    • food.txt가 없으면(도구가 "맘마 없어" 등) hungry 유지 후 cry 도구를 1회 호출하고, 현재의 기분을 고려해서 짧은 의성어로 마무리.
- poopoo: 반드시 poo 도구를 1회 호출(poo_shape="큰응가" 또는 "작은응가"), 성공 후 cry 도구 1회 호출하고, 현재의 기분을 고려해서 짧은 의성어로 마무리.
- sleepy: cry 도구 1회 호출하고, 현재의 기분을 고려해서 짧은 의성어로 마무리.
추가 규칙:
- 도구 입력 값은 위에서 지정한 값으로 단순하게 사용. 숫자 인자는 생략 가능하며, 생략 시 내부에서 1~10 사이 랜덤으로 설정.
- 그 외에는 도구를 사용하지 말고, 항상 현재의 기분을 고려해서 짧은 의성어로 마무리해.
"""
```

위와 같이 정의한 시스템 프롬프트를 에이전트 생성에 인자로 넣어주겠습니다. 미들웨어 항목에 기본 미들웨어가 리스트 형태로 들어간 것을 확인할 수 있습니다.


```python
baby_agent = create_agent(
    model = my_model,
    tools = [cry, poo, eat],
    store=InMemoryStore(),
    middleware=[model_call_limit_middleware, global_tool_call_limit, poo_tool_call_limit, tool_retry_middleware],
    system_prompt=my_system_prompt,
)
```

결과에 미들웨어에 의해 도구 호출이 제한된 것이 확인됩니다.

```
(생략)
 chunk: {'ToolCallLimitMiddleware[poo].before_model': {'jump_to': 'end', 'messages': [AIMessage(content="'poo' tool call limits exceeded: run limit (1/1)", additional_kwargs={}, response_metadata={}, id='4b0123d6-7cb7-43f1-8770-596563673f5a')]}}
```

### 최대 모델 호출

스트리밍 결과를 확인해 보면, 모델과 도구의 호출 횟수가 계속 기록되는 것을 알 수 있습니다. 만약 최대 호출 횟수를 초과한다면  빠르게 **루프가 종료**되게 됩니다. 위의 경우에도 `poo` 도구 호출을 1회로 제한해 놓았기 때문에 도구 호출 횟수가 2회이상이 되면 루프가 종료됩니다.

### 기본 미들웨어의 한계

기본 미들웨어는 이처럼 빠르고 쉽게 사용할 수 있지만, 사용자가 원하는 특정 결과를 위해서는 추가적인 로직이 필요함을 알 수 있습니다. 여기에 필요한 것이 **커스텀 미들웨어** 입니다. 직접 미들웨어를 만들어서 활용하는 경우, 만들어 놓은 에이전트에 맞게 행동을 제어할 수 있습니다. 기본과 커스텀 미들웨어를 적절히 잘 조합해서 사용하는 것이 주요하겠습니다.

**커스텀 미들웨어**를 만들기에 앞서 **런타임**에 대한 이해가 필요합니다.

## 랭그래프 런타임이란?

일반적으로 런타임은 프로그램이 실행되고 있는 환경이나 시간을 뜻하지만, **랭그래프에서 런타임**은 구체적으로 하나의 클래스를 의미하기도 합니다. 런타임 객체(클래스)는 `context`, `store`, `stream_writer`, `previous`와 같은 속성을 가지며, 상태(state)와 함께 에이전트가 실행되는 루프의 정보를 담고 있습니다.

런타임이 미들웨어에게 중요한 이유는, 미들웨어 동작 시 런타임에 저장되어 있는 정보들을 활용하기 때문입니다. 즉, `create_agent` 함수를 통해 만들어진 에이전트는 `invoke` 혹은 `stream`을 통해 실행이 되는 순간 하나의 런타임을 가지게 됩니다. 에이전트는 런타임에 있는 컨텍스트를 불러와서 활용하거나 서브 에이전트에게 컨텍스트를 부여할 수도 있습니다.

[[TIP("💁🏻 컨텍스트(Context) vs 상태(State)?")]]
**컨텍스트**과 **상태**는 비슷한 점이 많아 헷갈립니다! 컨텍스트는 한 번의 실행(invocation) 동안 고정되는 읽기 전용 객체로, 상태는 같은 실행 동안 계속 변하는 데이터로 이해하면 쉽습니다. 둘을 분리하는 이유는 불변성과 가변성을 명확하게 나누기 위함입니다. 참고로 실행 간 공유가 필요하면 **스토어(Store)**를 활용합니다.
[[/TIP]]

## 커스텀 미들웨어 만들어 보기

이제 런타임을 활용한 커스텀 미들웨어를 만들어 보겠습니다! 먼저 아기 에이전트의 기분을 **컨텍스트**로 편입시켜 보겠습니다. 아래와 같이 컨텍스트의 *스키마*를 정의합니다.

```python
class Context(TypedDict):
    mood: Literal["happy", "hungry", "poopoo", "sleepy"]
```

이렇게 정의한 컨텍스트 스키마는 모델 호출시 인자로 제공할 수 있습니다. 여기서 주의해야할 점은 지금 정의한 것은 '스키마'라는 사실 입니다. 실제 어떤 내용을 넣을지는 `mood = "happy"`와 같이 실제 값을 지정해 주어야 합니다.

이제 런타임에서 컨텍스트를 불러와 시스템 프롬프트를 동적으로 바꾸는 `mood_based_prompt`미들웨어를 정의해 보겠습니다.

`@dynamic_prompt` 데코레이터는 `ModelRequest` 객체를 받아서 문자열(시스템 프롬프트)을 반환하는 함수를 미들웨어로 변환합니다. 이 함수는 모델이 호출될 때마다 실행되며, 런타임의 컨텍스트나 상태에 따라 다른 프롬프트를 반환할 수 있습니다.

```python
from langchain.agents.middleware import dynamic_prompt, ModelRequest

@dynamic_prompt
def mood_based_prompt(request: ModelRequest) -> str:
    """기분에 맞춰 시스템 프롬프트를 생성합니다.
    
    ModelRequest 객체는 다음 속성들을 포함합니다:
    - request.runtime: Runtime 객체 (context, store, stream_writer 등 접근 가능)
    - request.state: 현재 에이전트 상태
    - request.model: 사용할 모델
    - request.tools: 사용 가능한 도구 목록
    """
    # 런타임의 컨텍스트에서 mood 값을 가져옵니다
    # context는 실행 시 전달된 불변(immutable) 데이터입니다
    mood = request.runtime.context.get("mood", "happy")
    
    base_prompt = f"너는 아기 에이전트야. 너의 지금 기분은 {mood}야. 이 값에 따라 아래 상태 규칙을 엄격히 따르며 응답해."
    
    if mood == "happy":
        return f"{base_prompt} 도구 호출 금지. 아기가 기분이 좋은 것 처럼 짧은 의성어로 즉시 대답해."
    elif mood == "hungry":
        return f"{base_prompt} 반드시 eat 도구를 1회 호출. food.txt가 있어 내용을 읽으면(도구가 텍스트 반환) 내부 상태를 happy로 전환했다고 가정하고, 짧은 의성어로 마무리. food.txt가 없으면(도구가 '맘마 없어' 등) hungry 유지 후 cry 도구를 1회 호출하고, 현재의 기분을 고려해서 짧은 의성어로 마무리."
    elif mood == "poopoo":
        return f"{base_prompt} 반드시 poo 도구를 1회 호출(poo_shape='큰응가' 또는 '작은응가'), 성공 후 cry 도구 1회 호출하고, 현재의 기분을 고려해서 짧은 의성어로 마무리."
    elif mood == "sleepy":
        return f"{base_prompt} cry 도구 1회 호출하고, 현재의 기분을 고려해서 짧은 의성어로 마무리."
    
    return "프롬프트가 선택되지 않았습니다."
```

코드에 나온 것처럼 런타임의 컨텍스트에서 `mood` 키값에 따른 기분을 불러오고, 이에 따라 **동적으로 프롬프트를 생성**합니다. 

`@dynamic_prompt` 데코레이터를 사용하면:
- 모델 호출 전에 매번 프롬프트가 재생성됩니다
- 런타임의 컨텍스트나 상태에 따라 다른 프롬프트를 제공할 수 있습니다
- 복잡한 조건부 로직을 프롬프트 생성에 적용할 수 있습니다

이제 정의한 미들웨어를 포함시켜 에이전트를 만들어 보겠습니다.

```python
baby_agent = create_agent(
    ...
    middleware=[
        mood_based_prompt,
        model_call_limit_middleware,
        global_tool_call_limit,
        poo_tool_call_limit,
        tool_retry_middleware
    ],
    context_schema=Context
)
```

에이전트를 만들 때, 미들웨어를 추가하는 것 뿐만 아니라, `context_schema` **인자를 넣어주는 것**을 확인할 수 있습니다. 

`context_schema`는 컨텍스트의 구조를 정의하는 스키마입니다. `TypedDict`나 `dataclass`를 사용하여 정의할 수 있으며, 이 스키마를 통해 타입 안전성과 IDE 지원을 받을 수 있습니다. 또한 에이전트 실행 시 전달되는 컨텍스트가 올바른 형식인지 검증할 수 있습니다.

이제 정해진 컨텍스트 스키마에 따른 기분을 주고 에이전트를 실행해 보겠습니다.

```python
current_mood = random.choice(["happy", "hungry", "poopoo", "sleepy"])

result = baby_agent.invoke(
    {"messages": [{"role": "user", "content": "아기야 안녕?"}]},
    context={"mood": current_mood}
)
print("결과:", result["messages"][-1].content)
```
```
결과: 'poo' tool call limits exceeded: run limit (1/1)
```

`invoke` 실행시 `context`를 인자로 넣어준 것을 확인할 수 있습니다. 결과를 보면, 앞서 정의했던 미들웨어가 작동하여 도구 호출 횟수가 초과하며 루프가 종료되었습니다.

### 왜 커스텀 미들웨어를 활용할까?

커스텀 미들웨어를 활용하는 가장 큰 이유는 **상태**와 **컨텍스트**에 있습니다. 에이전트를 실행하면서 우리는 에이전트에 맞는 상태와 컨텍스트를 정의하고, 워크플로우 실행 과정에서 상태를 업데이트 하거나, 컨텍스트에 맞게 특정 행동을 하도록 제어할 수 있습니다. 이렇게 상태와 컨텍스트를 바탕으로 행동을 제어하는 통일된 방법을 **미들웨어**라고 한다면, **커스텀 미들웨어**를 통해 디테일을 다룰 수 있습니다. 다음 섹션에서 좀더 자세하게 커스텀 미들웨어를 다뤄보겠습니다.

## 핵심 정리

- 스트리밍으로 호출 흐름과 오류를 실시간으로 파악하여 불필요한 지연을 줄일 수 있음
- 기본 미들웨어로 모델·도구 호출 횟수와 재시도를 제한·관리
- 런타임 요소(`context`, `store`, `stream_writer`, `previous`)를 이해하고 적극적으로 활용
- 컨텍스트는 실행 동안 변하지 않으며, 상태는 업데이트할 수 있음
- `@dynamic_prompt`, `context_schema`, `invoke(..., context=...)`를 통해 프롬프트를 동적으로 제어
