에이전트에게 적절한 **맥락(context)** 을 제공하는 것은 성능에 필수적인 요소입니다. 맥락에 주어진 정보에 따라 성능이 천차만별로 달라지고, 맥락의 구성에 따라 할루시네이션이 발생하기도 합니다.

에이전트를 만들다 보면 헷갈리는 부분이 맥락과 상태의 구분입니다. 에이전트의 데이터를 '저장'하고 '업데이트'하는 것이 **상태(state)**라면, '실행'을 위한 '정보'를 주는 것이 **컨텍스트**입니다. 컨텍스트는 상태보다 넓은 개념으로 볼 수 있습니다. 상태가 컨텍스트의 일부로 활용되기도 하며, 실행 환경, 런타임 정보, 요청 세부사항 등을 포함해서 부르기도 합니다.

이번 섹션에서는 컨텍스트의 개념에 대해 알아보고, 앞서 만든 아기 에이전트를 바탕으로 어떻게 컨텍스트 엔지니어링을 해왔는지 복습해 보겠습니다.

## 📚 컨텍스트의 종류

컨텍스트는 에이전트 활용 단계를 기준으로크게 아래와 같이 구분할 수 있습니다: [랭체인 컨텍스트 엔지니어링](https://docs.langchain.com/oss/python/langchain/context-engineering).

|종류|제어항목|메모리|
|:--:|:--:|:--:|
|모델 컨텍스트|모델 호출시 들어가는 컨텍스트: 프롬프트, 답변 구조, 대화 히스토리, 도구등을 제어|휘발성|
|도구 컨텍스트|도구가 접근할 수 있는 컨텍스트: 상태, 스토어, 런타임 등을 업데이트 하고 제어|비휘발성|
|라이프사이클 컨텍스트|모델과 도구 호출 과정 전반에서 발생하는 컨텍스트: 대화 요약, 로그 등을 지원|비휘발성|

먼저 **모델 컨텍스트** 엔지니어링에 대해 알아보겠습니다.

## 모델 컨텍스트 엔지니어링

모델 컨텍스트는 대체로 프롬프트, 메시지, 도구 호출, 결과 구조화와 관련이 깊습니다. 아기 에이전트를 만드는 과정에서 상황에 맞게 시스템 프롬프트를 호출한 것을 기억해 봅시다. 

```python
def before_model(self, state: AgentState["BabyResponse"], runtime):
    messages = state.get("messages", [])
    if messages:
        last_message = messages[-1]
        if isinstance(last_message, ToolMessage):
            name = getattr(last_message, "name", "")
            content = getattr(last_message, "content", "")

            if name == "eat" and "맘마를 먹었어요" in content:
                return {"action": None, "mood": "happy"}
            elif name == "eat" and "맘마 없어" in content:
                return {"action": "cry", "mood": "hungry"}
            elif name in ("cry", "poo"):
                return {"action": None, "mood": "happy"}

    mood = state.get("mood", "happy")
    if state.get("action") is None and mood in ("poopoo", "sleepy", "hungry"):
        action_map = {"poopoo": "poo", "sleepy": "cry", "hungry": "eat"}
        return {"action": action_map[mood]}

    print(f"지금은 행동 준비 중, 기분은 {mood}에요!")
    return
```

우리는 미들웨어의 `before_model` 메소드를 통해 모델에 어떤 **상태**(기분, 행동)이 들어가는지 제어했습니다. 이는 **상태를 업데이트 하는 컨텍스트 엔지니어링**에 속합니다. 다음으로 `wrap_model_call` 메소드를 보겠습니다.

또한 `if isinstance(last_message, ToolMessage):` 로 시작하는 구문을 보면, 도구 호출과 관련된 메시지를 불러와서 모델에게 제공하고 상태를 업데이트 합니다. 이는 **메시지를 활용한 모델 컨텍스트 엔지니어링**에 속합니다.

다음으로 프롬프트와 관련된 메소드를 살펴보겠습니다.

```python
def wrap_model_call(self, request: ModelRequest, handler) -> ModelResponse:
    mood = request.state.get("mood", "happy")
    action = request.state.get("action", None)

    base_prompt = f"지금 너의 기분은 {mood}야. 매우 짧은 한국어 아기 의성어만."

    if action in ("cry", "poo", "eat"):
        tool_name = action
        system_prompt = f"{base_prompt} 이번 턴에는 반드시 {tool_name} 도구를 호출해"
        request.response_format = None
    else:
        tool_name = None
        system_prompt = base_prompt
        request.tools = []

    # Set system prompt and filter tools
    request.system_prompt = system_prompt
    if tool_name:
        request.tools = [t for t in request.tools if getattr(t, "name", None) == tool_name]

    return handler(request)
```

여기서 모델에 어떤 프롬프트가 들어갈지 상황에 맞춰 동적으로 제어했습니다. 이는 **프롬프트를 제어하는 컨텍스트 엔지니어링**에 속합니다.

역시 어떤 도구를 활용할지 `request.tools = [t for t in request.tools if getattr(t, "name", None) == tool_name]`와 같이 제어한 부분은 **도구 선택을 제어하는 모델 컨텍스트 엔지니어링**에 속합니다.

추가로 `BabyResponse`클래스를 활용하여 답변을 구조화한 것 역시 모델 컨텍스트 엔지니어링에 속합니다.

이제 **도구 컨텍스트 엔지니어링**을 살펴보겠습니다.

## 도구 컨텍스트 엔지니어링

```python
def wrap_tool_call(self, request, handler):
    tool_name = getattr(request.tool, "name", request.tool_call.get("name"))
    args = request.tool_call.setdefault("args", {})

    if tool_name == "cry":
        args["cry_count"] = random.randint(1, 10)
    elif tool_name == "poo":
        args["poo_count"] = random.randint(1, 10)
        args["poo_shape"] = random.choice(["큰응가", "작은응가"])

    return handler(request)
```

미들웨어에서 `wrap_tool_call` 메소드를 통해, 도구에 어떤 인자를 넣을지 제어했습니다. 이처럼 도구를 정의하거나 선택하고 직접 호출하는 과정에서 정보를 활용하는 것을 **도구 컨텍스트 엔지니어링**이라고 부르겠습니다.

마지막으로 라이프 사이클 컨텍스트 엔지니어링을 살펴보겠습니다.

## 라이프사이클  컨텍스트 엔지니어링

에이전트의 라이프사이클을 제어하는 컨텍스트 엔지니어링은 보통 너무 길어진 메시지를 **요약**하거나, 전반적인 실행 과정에서 예상 범위를 벗어나지 않도록 제어하는 것을 칭합니다. 아기 에이전트에서 `initial_mood = random.choice(["happy", "hungry", "poopoo", "sleepy"])`를 통해 초기 기분을 넷 중 하나로 고정한 것이나,

```python
class BabyState(AgentState["BabyResponse"]):
    mood: Literal["happy", "hungry", "poopoo", "sleepy"]
    action: NotRequired[Literal["cry", "poo", "eat"]]
```

위와 같이 스키마를 정의하여 상태를 만들고 제어하는 것 역시 **라이프 사이클 컨텍스트 엔지니어링**의 일환으로 이해할 수 있습니다. 마찬가지로 스키마와 도구에 설명을 구체적으로 추가하여

```python
@tool("eat", description="맘마를 먹습니다. 디렉토리에 있는 food.txt 파일을 읽고 내용을 지웁니다. 없으면 배고픔 상태를 기록합니다.")

response: str = Field(..., description="아기 에이전트의 기분에 따른 짧은 의성어 답변")
```

위와 같이 상태/도구와 관련된 정보를 제공하는 것도 **라이프 사이클 컨텍스트 엔지니어링** 입니다.

## 그냥 다 컨텍스트 엔지니어링 이라고 하는거 아니야?

맞습니다. 지금으로선 에이전트가 의도대로 동작하도록 맥락을 제공하는것과 관련된 행위를 **컨텍스트 엔지니어링**으로 통칭했습니다. 어쩌면 **컨텍스트 엔지니어링**이 좋은 에이전트를 만들기 위한 알파이자 오메가이기 때문에, *모든 길은 로마로 통한다*는 말처럼 모든 것이 **컨텍스트 엔지니어링**으로 이어지는지도 모르겠습니다.

추후 랭그래프를 활용하여 보다 세밀하게 에이전트의 워크플로우를 제어하는 과정에서는 굳이 컨텍스트를 필요로 하지 않는 워크플로우를 다룰 수도 있고, **상태**라는 보다 세분화된 개념을 중심으로 다룰수도 있습니다. **컨텍스트**는 보다 광범위한 개념으로 이해하는 것도 괜찮겠습니다.

이번 섹션에서 기억해야 할 한가지는, 랭체인/랭그래프 에이전트의 성패는 **미들웨어**를 통해 **컨텍스트** 제어하는데에 있다는 점입니다. **상태**, **런타임**, **스토어**등의 데이터를 참고하여 의도대로 에이전트를 제어하는 것이 중요한 만큼, 이에 대한 개념을 숙지하고 넘어가는 것이 좋겠습니다.

## 핵심 정리
- **에이전트 실패의 주 원인:** 올바른 컨텍스트의 부족
- **컨텍스트 엔지니어링:** 적절한 정보와 도구를 에이전트에게 제공하는 것
- **3가지 컨텍스트 타입:** 모델 컨텍스트, 도구 컨텍스트, 라이프사이클 컨텍스트
- **미들웨어의 역할:** 상태/런타임/스토어 데이터를 활용해 컨텍스트를 동적으로 제어
- **성공의 열쇠:** 모든 에이전트 제어는 컨텍스트 엔지니어링으로 귀결됨
