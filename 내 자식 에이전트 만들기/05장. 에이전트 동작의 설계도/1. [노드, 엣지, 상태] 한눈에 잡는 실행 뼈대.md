이 페이지에서는 에이전트의 핵심을 이루는 **노드(Node)**·**엣지(Edge)**·**상태(State)**, 그리고 이들이 결합되어 동작하는 **그래프(Graph)**의 구조를 살펴봅니다.  

LangGraph는 이러한 그래프 개념을 기반으로 에이전트의 전체 동작 흐름을 제어합니다.  

이번 페이지의 목표는 `router → (ask_clarify | call_tool | finalize) → end` 형태의 **기본 그래프 설계**를 이해하고,  
각 구성 요소가 어떤 역할을 하며 어떻게 상호작용하는지를 코드 예시와 함께 익히는 것입니다.  



## 그래프 자료구조

우리가 일상에서 다루는 데이터 구조에는 여러 형태가 있습니다.  
그중 **그래프(Graph)** 는 수학과 컴퓨터 과학에서 널리 사용되는 구조로, **정점(Vertex)** 과 **간선(Edge)** 의 집합으로 이루어집니다.  

**LangGraph**는 이러한 그래프 이론을 **AI 에이전트 개발**에 응용한 프레임워크입니다.  
전통적인 그래프가 정적이고 단순한 연결 관계를 표현하는 데 그쳤다면, LangGraph는 **동적 실행**, **상태 기반 데이터 흐름**, **조건부 분기**를 지원합니다.  
즉, 단순한 “연결 구조”가 아니라 **실행 가능한 제어 흐름(Workflow)** 을 표현하는 그래프입니다.

LangGraph의 핵심 철학은 **상태 기반 그래프(State-based Graph)** 구현에 있습니다.  
모든 노드는 **공유 상태(State)** 를 통해 데이터를 주고받으며, 각 노드는 **순수 함수(Pure Function)** 로 작성되어 함수형 프로그래밍의 장점을 적극 활용합니다.  

LangGraph는 다음과 같은 특징을 갖습니다.

- **상태 중심 설계** : 모든 노드가 동일한 상태 객체를 공유  
- **함수형 패러다임** : 순수 함수 기반의 독립적 노드  
- **선언적 흐름** : 코드로 실행 순서를 명시적으로 표현  
- **타입 안전성** : Python 타입 힌트를 통한 안정적인 개발



## 노드(Node)

![](https://wikidocs.net/images/page/299477/image_202510211447.png)

### 이론적 배경

**노드(Node)** 는 그래프에서 **실제 작업을 수행하는 최소 단위 함수**입니다.  
함수형 프로그래밍의 핵심 개념인 **순수 함수(Pure Function)** 를 기반으로 합니다.

순수 함수의 특징:
1. 동일한 입력에 대해 항상 동일한 출력을 반환합니다.  
2. 외부 상태를 변경하지 않습니다.  
3. 입력과 출력이 명확하여 독립적으로 테스트가 가능합니다.

이러한 특성 덕분에 LangGraph의 각 노드는 **독립적**, **재사용 가능**, **예측 가능한 단위 모듈**이 됩니다.

> 💡 **예시: 순수 함수로서의 노드**
```python
from typing import TypedDict

class MyState(TypedDict):
    counter: int  # 작업 영역의 예: 카운터 값

def increment(state: MyState) -> MyState:
    # 기존 상태를 직접 수정하지 않고, 새로운 사본을 만들어 반환 (불변성)
    return {**state, "counter": state["counter"] + 1}

# 데모
s0 = {"counter": 0}
s1 = increment(s0)

print(s0)  # {'counter': 0}  ← 원본 상태는 유지됨
print(s1)  # {'counter': 1}  ← 새로운 상태만 변경됨
```
---

### 설계 원칙

노드를 설계할 때는 다음의 원칙을 따릅니다.

- **단일 책임 원칙(Single Responsibility Principle)** : 한 노드는 한 가지 일만 한다.  
- **상태 불변성(Immutability)** : 기존 상태를 수정하지 않고 새 상태를 반환한다.  
- **명시적 예외 처리** : 오류나 누락 상태를 명확히 기록한다.  
- **로깅(Logging)** : 실행 과정을 추적 가능하게 한다.

LangGraph에서 노드는 `state`를 입력받아 처리 후 **새로운 state**를 반환합니다.  
모든 노드는 독립적으로 실행 가능하며, 다른 그래프에서도 재사용할 수 있습니다.

> 💡 **예시: 로깅과 예외 처리 포함**
```python
 import logging
 logging.basicConfig(level=logging.INFO)
 def safe_divide(state: dict, denom: int) -> dict:
     try:
         return {**state, "value": state["value"] // denom}
     except ZeroDivisionError:
         logging.error("Zero division!")
         return {**state, "error": "DIV_ZERO"}

 safe_divide({"value": 10}, 2)
 # {'value': 5}
```

---

📘 **정리**
- 노드는 상태를 입력받아 새로운 상태를 반환하는 **순수 함수**다.  
- 모든 노드는 **불변성**, **단일 책임성**, **명시적 예외 처리** 원칙을 따른다.



## 엣지(Edge)

**엣지(Edge)** 는 노드 간의 **실행 흐름(Control Flow)** 을 정의하는 요소입니다.  
즉, 한 노드가 끝난 뒤 **어떤 노드로 이동할지**를 결정하는 역할을 합니다.  

기본적인 제어 흐름 유형은 다음과 같습니다.

| 유형 | 설명 |
|------|------|
| **순차 실행** | 한 노드에서 다음 노드로 순서대로 진행 |
| **조건부 분기** | 특정 조건에 따라 다른 경로로 이동 |
| **병렬 실행** | 여러 노드를 동시에 실행 |
| **순환 구조(Loop)** | 조건이 충족될 때까지 반복 실행 |


엣지를 설계할 때는 다음 사항을 고려합니다.

- **명확성**: 실행 흐름이 직관적이어야 한다.  
- **유연성**: 다양한 조건 분기에 대응할 수 있어야 한다.  
- **효율성**: 불필요한 실행을 줄여 성능을 확보한다.  
- **추적성**: 실행 경로를 로깅 및 디버깅할 수 있어야 한다.

---

LangGraph의 엣지는 단순한 “연결선”이 아니라,  
**조건부 실행 경로를 포함한 제어 규칙(Control Rule)** 로서 작동합니다.  

즉, 단순 엣지는 항상 동일한 다음 노드로 이동하지만,  
**조건부 엣지 (Conditional Edges)**는 `if / else` 형태로 분기하여 다른 노드로 이동할 수 있습니다.

![](https://wikidocs.net/images/page/299477/image_202510211513.png)

 ✍️ **조건부 라우팅(Edge Rule)**  
 
 아래 예시는 `state`의 조건에 따라 다음 노드로 분기하는 단순한 라우터(엣지 규칙)입니다.  

 ```python
def router(state):
     if "missing" in state:
         # 필수 정보가 없을 때 → 재질문 노드로 이동
         return "ask_clarify"
     elif state.get("needs_tool"):
         # 외부 도구 호출이 필요한 경우 → call_tool로 이동
         return "call_tool"
     else:
         # 모든 조건이 충족되면 → 최종 단계로 이동
         return "finalize"
 # 예시 실행
 print(router({"missing": True}))       # 'ask_clarify'
 print(router({"needs_tool": True}))    # 'call_tool'
 print(router({"done": True}))          # 'finalize'
```


 **핵심 포인트**
 - 엣지는 단순 연결이 아니라 **조건 기반의 흐름 제어 규칙**이다.  
 - `router`는 현재 상태(`state`)를 읽고 다음 실행 노드를 결정한다.

## 상태(State) — 확장판

**상태(State)**는 그래프 실행의 “현재 맥락”을 담는 단일 데이터 객체이며, 노드 간 정보 전달의 매개이자 분기 판단의 근거입니다. 상태를 잘 설계하면 흐름 제어가 단순해지고, 테스트·디버깅·재현이 쉬워집니다. 반대로 상태가 느슨하면 노드 복잡도가 급격히 증가하고, 오류 원인 추적이 어려워집니다.

### 역할과 경계

상태는 다음 세 가지 관점을 명확히 분리해 설계합니다.

- **입력 영역(Input)**: 사용자 입력, 시스템 초기 컨텍스트 등 변경되지 않아야 하는 값.  
- **작업 영역(Working)**: 노드들이 읽고 쓰며 중간 산출물을 담는 값.  
- **출력 영역(Output)**: 사용자에게 전달되거나 외부 시스템으로 내보낼 최종 결과.  

그래프 외부 자원(파일, DB, 네트워크)은 상태에 **참조(URI, 키, 해시)**만 남기고, 원본을 직접 담지 않습니다.

> ✍️ **TypedDict로 얕은 계층의 상태 스키마**

가장 단순한 형태의 상태 스키마부터 출발해 보겠습니다.  
`router` 예제에서 사용한 필드만 뽑아 보면 다음과 같이 정의할 수 있습니다.

```python
from typing import TypedDict

class RouterState(TypedDict, total=False):
    missing: bool
    needs_tool: bool
    done: bool
```

여기에 01~03장에서 다룬 메시지 기반 상태를 섞어 쓰고 싶다면, LangGraph v1이 제공하는 `MessagesState`를 그대로 가져와 확장하는 방식이 가장 안전합니다.

```python
from langgraph.graph import MessagesState

class AgentState(MessagesState):
    missing: bool
    needs_tool: bool
    done: bool
```

이렇게 하면:

- 메시지 히스토리는 `MessagesState` + `add_messages` 리듀서로 표준 관리
- 분기 조건은 `missing` / `needs_tool` / `done` 같은 얕은 불리언 필드로 제어

라는 역할 분담이 자연스럽게 생깁니다. 디버깅할 때도 Studio에서 상태를 펼쳐 보면, “어떤 플래그 때문에 어디로 분기됐는지”를 한눈에 확인할 수 있습니다.

## 기본 그래프 설계 (router → ask_clarify | call_tool | finalize → end)

> ✍️ **구조**

지금까지 살펴본 개념을 바탕으로, LangGraph v1의 `StateGraph`로 최소 실행 그래프를 그려 보면 다음과 같습니다.

```python
from langgraph.graph import StateGraph, START, END

def router(state: AgentState) -> str:
    if state.get("missing"):
        return "ask_clarify"
    elif state.get("needs_tool"):
        return "call_tool"
    else:
        return "finalize"

builder = StateGraph(AgentState)

builder.add_node("ask_clarify", ask_clarify_node)
builder.add_node("call_tool", call_tool_node)
builder.add_node("finalize", finalize_node)

builder.add_edge(START, "router")
builder.add_conditional_edges("router", router,  # 상태에 따라 분기
    {
        "ask_clarify": "ask_clarify",
        "call_tool": "call_tool",
        "finalize": "finalize",
    },
)
builder.add_edge("ask_clarify", "router")
builder.add_edge("call_tool", "router")
builder.add_edge("finalize", END)

graph = builder.compile()
```

이 그래프는 다음과 같은 특징을 갖습니다.

- 항상 `router`를 통해 다음 단계가 결정되므로, **실행 경로를 추적·재현**하기 쉽다.
- Studio에서 실행해 보면, 어느 상태에서 `ask_clarify`로 갔는지, 언제 `finalize`로 종료됐는지 한눈에 보인다.
- 나중에 멀티 에이전트, 서브그래프, HITL를 도입해도 이 “ASK | CALL | FINAL” 뼈대는 그대로 유지된다.


## 타입 안전성과 스키마 선택 가이드

LangChain/LangGraph v1에서는 상태 스키마를 위해 보통 다음 중 하나를 선택합니다.

- `TypedDict`: 가볍고 표준 라이브러리만으로 충분할 때
- `dataclasses`: 약간 더 구조화된 객체 스타일이 필요할 때
- `Pydantic` 모델: 검증·직렬화·문서화까지 한 번에 처리하고 싶을 때

어떤 것을 선택하든, 다음 두 가지 원칙만 꼭 지켜 주세요.

- **얕은 계층**: 중첩 딕셔너리 대신, 상위 수준에서 의미 있는 필드 이름을 사용한다.
- **명확한 네이밍**: `missing`, `needs_tool`, `done`처럼 “분기 조건”이 변수 이름만 보고도 이해되게 쓴다.

이렇게 해 두면 나중에 Studio에서 상태를 펼쳐 보거나, 체크포인트를 파일로 저장해 다시 로드할 때도 “이 값이 왜 이렇게 되었는지”를 추적하기 쉬워집니다.

## 마무리 체크리스트

- 노드는 **단일 책임**과 **순수 함수** 원칙을 따른다.  
- 엣지는 **조건 명시**로 경로를 분기하고, 병렬·루프를 단순 규칙으로 다룬다.  
- 상태는 **입력/작업/출력** 영역을 나눠 설계하고 **불변성**을 유지한다.  
- 메시지·모델·툴은 **명확한 인터페이스**로 연결한다.  
- 라우터는 `ASK | CALL | FINAL`의 **짧은 분기 규칙**으로 설계한다.  
- 로깅·테스트를 통해 **추적성과 재현성**을 보장한다.
