지금까지 배운 Store와 Retrieval을 활용하여, 이제 실제 데이터베이스와 상호작용하는 SQL 에이전트를 만들어봅시다. SQL 에이전트는 자연어 질문을 받아 SQL 쿼리를 생성하고 실행하여 데이터베이스에서 정보를 가져오는 강력한 도구입니다. 6장에서 본 멀티 에이전트·서브그래프 패턴과 결합하면, “SQL 담당 에이전트”를 하나의 서브그래프로 두고 다른 에이전트들과 협업시키는 구조도 쉽게 만들 수 있습니다.

SQL 에이전트는 비즈니스 인텔리전스, 데이터 분석, 고객 지원 등 다양한 분야에서 활용될 수 있습니다. 예를들어 사용자가 "지난 달에 가장 많이 팔린 상품 10개를 알려줘"라고 질문하면, SQL 에이전트는 이를 SQL 쿼리로 변환하고 실행하여 결과를 제공할 수 있습니다. 이는 비기술자도 복잡한 데이터베이스 쿼리를 자연어로 수행할 수 있게 해주는 혁신적인 기술입니다.

하지만 SQL 에이전트를 구축하는 것은 단순하지 않습니다. 데이터베이스 스키마를 이해하고, 사용자의 의도를 파악하여 올바른 쿼리를 생성해야 하며, 보안 문제도 고려해야 합니다. 잘못된 쿼리가 실행되면 데이터베이스에 심각한 문제를 일으킬 수 있기 때문입니다.

이번 섹션에서는 LangGraph의 StateGraph를 사용하여 SQL 에이전트를 만드는 방법을 배워봅시다. 2장에서 배운 ReAct 패턴을 활용하여 에이전트가 스스로 데이터베이스를 탐색하고 올바른 쿼리를 생성하도록 만들어보겠습니다.

데이터베이스에 수백 개의 테이블과 수천 개의 컬럼이 있다고 생각해봅시다. 사용자가 "가장 많이 팔린 상품 10개를 알려줘"라고 질문했을 때, 어떤 테이블을 조회해야 할지, 어떤 컬럼을 사용해야 할지 알아야 합니다. 

전통적인 방식이라면, 데이터베이스 관리자나 개발자가 SQL 쿼리를 직접 작성해야 합니다. 하지만 이는 여러 문제점이 있습니다. 첫째, SQL을 모르는 사용자는 데이터베이스에 접근할 수 없습니다. 둘째, 스키마가 복잡할수록 올바른 쿼리를 작성하기 어려워집니다. 셋째, 스키마가 변경되면 코드도 함께 수정해야 합니다.

SQL 에이전트는 이러한 문제를 해결합니다. 사용자는 자연어로 질문할 수 있고, 에이전트가 자동으로 적절한 SQL 쿼리를 생성하고 실행합니다. 이는 데이터 접근성을 크게 향상시키고, 비즈니스 사용자도 직접 데이터를 분석할 수 있게 해줍니다.

SQL 에이전트는 다음과 같은 역할을 수행합니다. 사용자의 자연어 질문을 분석하여 적절한 SQL 쿼리로 변환하고, 데이터베이스의 테이블과 컬럼 구조를 자동으로 파악하며, 생성된 쿼리가 올바른지 검증하고 에러가 발생하면 수정하며, SQL 쿼리 결과를 사용자가 이해하기 쉬운 자연어로 변환하여 제공합니다.

전통적인 SQL 쿼리 작성 방식은 다음과 같은 한계가 있습니다. SQL 문법을 알고 있어야 하며 복잡한 쿼리는 작성이 어렵고, 데이터베이스 스키마가 변경되면 관련된 모든 코드를 수정해야 하며, JOIN, 서브쿼리 등을 사용한 쿼리는 작성과 유지보수가 어렵고, SQL을 모르는 사용자는 데이터베이스에 접근할 수 없습니다.

SQL 에이전트는 모델이 생성한 SQL 쿼리를 실행합니다. 실수로 데이터를 삭제하거나 수정할 수 있으므로 주의가 필요합니다. 데이터를 변경할 수 없도록 읽기 전용 권한만 사용하고, INSERT, UPDATE, DELETE 같은 명령은 사용하지 않습니다. 시스템 프롬프트에 "SELECT 쿼리만 사용하라"고 명확히 지시해야 합니다. 학습 단계에서는 SQLite 예제 데이터베이스를 사용하고, 실제 데이터가 있는 데이터베이스에서는 읽기 전용 권한만 사용하세요. 시스템 프롬프트에 "Only use SELECT queries"라고 명시하는 것도 중요합니다.

먼저 필요한 패키지를 설치합니다.

```bash
pip install -U langchain langchain-community langgraph langchain-openai
```

SQLite 예제 데이터베이스를 사용하겠습니다. 실제 프로덕션에서는 PostgreSQL이나 다른 데이터베이스를 사용할 수 있습니다.

```python
from langchain_community.utilities import SQLDatabase
from langchain_community.agent_toolkits import SQLDatabaseToolkit
from langchain_openai import ChatOpenAI

# SQLite 데이터베이스 연결
db = SQLDatabase.from_uri("sqlite:///chinook.db")

# LLM 초기화
llm = ChatOpenAI(model="gpt-4o", temperature=0)

# SQL 도구 생성
toolkit = SQLDatabaseToolkit(db=db, llm=llm)
tools = toolkit.get_tools()

print("사용 가능한 SQL 도구:")
for tool in tools:
    print(f"- {tool.name}: {tool.description}")
```

실행하면 다음과 같은 결과가 나옵니다:

```
사용 가능한 SQL 도구:
- sql_db_list_tables: Input to this tool is a comma-separated list of table names, output is the schema and sample rows for those tables.
- sql_db_schema: Input is a comma-separated list of tables, output is the schema of those tables.
- sql_db_query: Input to this tool is a detailed and correct SQL query, output is a result from the database.
```

이제 LangGraph의 StateGraph를 사용하여 SQL 에이전트를 만들어보겠습니다. 2장에서 배운 ReAct 패턴을 활용하여 `assistant → tools → assistant` 루프를 구성하겠습니다.

SQL 에이전트를 만들기 위해서는 먼저 데이터베이스에 연결해야 합니다. 여기서는 SQLite 데이터베이스를 사용하겠습니다.

```python
from langchain_community.utilities import SQLDatabase

# SQLite 예제 데이터베이스 사용
db = SQLDatabase.from_uri("sqlite:///chinook.db")
```

`SQLDatabase.from_uri`는 데이터베이스 연결 문자열을 받아서 `SQLDatabase` 객체를 생성합니다. `sqlite:///chinook.db`는 현재 디렉토리에 있는 `chinook.db` 파일을 사용한다는 의미입니다. `chinook.db`는 SQLite 예제 데이터베이스이며, 실제 프로젝트에서는 자신의 데이터베이스 경로를 사용하면 됩니다.

```python
# 테이블 목록 확인
print("데이터베이스 테이블:")
print(db.get_usable_table_names())
```

데이터베이스에 어떤 테이블이 있는지 확인합니다. `get_usable_table_names()` 메서드는 데이터베이스에 있는 모든 테이블의 이름을 리스트로 반환합니다. 에이전트가 어떤 테이블을 사용할 수 있는지 알아야 올바른 쿼리를 생성할 수 있기 때문입니다.

이제 LangGraph의 StateGraph를 사용하여 SQL 에이전트를 구성하겠습니다. 2장에서 배운 ReAct 패턴을 활용합니다.

```python
from langchain_openai import ChatOpenAI
from langchain_community.agent_toolkits import SQLDatabaseToolkit
from langchain_core.messages import SystemMessage
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition

# LLM 초기화
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
```

먼저 LLM을 초기화합니다. `temperature=0`으로 설정하여 일관된 결과를 얻도록 합니다.

```python
# SQL 도구 생성
toolkit = SQLDatabaseToolkit(db=db, llm=llm)
tools = toolkit.get_tools()
```

`SQLDatabaseToolkit`는 SQL 데이터베이스와 상호작용하기 위한 도구들을 제공합니다. 이 툴킷은 `sql_db_list_tables`로 데이터베이스의 테이블 목록을 가져오고, `sql_db_schema`로 특정 테이블의 스키마(컬럼 정보)를 가져오며, `sql_db_query`로 SQL 쿼리를 실행하고 결과를 반환하고, `sql_db_query_checker`로 쿼리가 올바른지 검증합니다. `get_tools()` 메서드를 호출하면 이러한 도구들의 리스트를 얻을 수 있습니다.

```python
# 도구를 LLM에 바인딩 (ReAct는 순차 실행이 중요하므로 parallel_tool_calls=False)
llm_with_tools = llm.bind_tools(tools, parallel_tool_calls=False)

# 시스템 메시지 정의
system_msg = SystemMessage(
    content="""You are a SQL database assistant.
Given a question, you should:
1. List available tables
2. Get schema of relevant tables  
3. Generate and execute a SQL query
4. Return the results in a natural way

IMPORTANT: Only use SELECT queries. Never modify the database."""
)
```

시스템 메시지를 정의합니다. 이 메시지는 에이전트에게 어떻게 동작해야 하는지 지시합니다. 사용 가능한 테이블 목록을 확인하고, 관련 테이블의 스키마를 가져오며, SQL 쿼리를 생성하고 실행하고, 결과를 자연스러운 언어로 반환합니다.

중요한 보안 규칙은 "Only use SELECT queries. Never modify the database."라는 지시를 통해 에이전트가 데이터를 변경하는 쿼리(INSERT, UPDATE, DELETE)를 실행하지 않도록 하는 것입니다. ReAct 패턴에서는 순차적 실행이 중요하므로 `parallel_tool_calls=False`로 설정합니다.

```python
# Assistant 노드 정의
def assistant(state: MessagesState):
    """ReAct 에이전트의 추론(Reasoning) 단계"""
    return {"messages": [llm_with_tools.invoke([system_msg] + state["messages"])]}
```

Assistant 노드를 정의합니다. 이 노드는 현재 메시지 히스토리와 시스템 메시지를 합쳐서 LLM을 호출하고, 필요하면 도구를 호출하도록 합니다.

```python
# 그래프 구성
builder = StateGraph(MessagesState)

# 노드 추가
builder.add_node("assistant", assistant)
builder.add_node("tools", ToolNode(tools))

# 엣지 정의
builder.add_edge(START, "assistant")
builder.add_conditional_edges("assistant", tools_condition)  # 도구 호출 여부 판단
builder.add_edge("tools", "assistant")  # 도구 실행 후 다시 추론
builder.add_edge("assistant", END)  # 더 이상 도구 호출 없으면 종료

# 그래프 컴파일
sql_agent = builder.compile()
```

StateGraph를 사용하여 ReAct 루프를 구성합니다. `assistant` 노드는 추론 및 도구 호출 판단을 하고, `tools` 노드는 도구를 실행하며, `tools_condition`은 도구 호출이 필요한지 판단하는 조건부 엣지입니다. 루프 구조는 `assistant → tools → assistant`로 반복됩니다. 이렇게 하면 에이전트가 필요에 따라 여러 번 도구를 호출하면서 문제를 단계별로 해결할 수 있습니다.

이제 만든 SQL 에이전트를 실행해보겠습니다. 두 가지 질문을 해보겠습니다.

실제 시나리오를 가정해보겠습니다. 온라인 음악 스토어의 데이터 분석 에이전트를 만든다고 생각해봅시다. 비즈니스 팀이 "가장 인기 있는 아티스트는 누구인가요?" 또는 "올해 가장 많이 팔린 앨범은 무엇인가요?"와 같은 질문을 자연어로 할 수 있도록 해야 합니다.

```python
from langchain_core.messages import HumanMessage

# 질문 1: 데이터베이스 구조 파악
result1 = sql_agent.invoke({
    "messages": [
        HumanMessage(content="데이터베이스에 어떤 테이블들이 있나요?")
    ]
})
```

첫 번째 질문은 데이터베이스에 어떤 테이블이 있는지 묻는 것입니다. 실제로는 비즈니스 팀이 데이터베이스 구조를 모를 수 있으므로, 에이전트가 먼저 어떤 테이블들이 있는지 파악해야 합니다.

에이전트는 내부적으로 다음과 같은 과정을 거칩니다. 먼저 assistant 노드가 사용자 질문을 분석하고, "데이터베이스 구조를 파악하려면 테이블 목록이 필요하다"고 판단합니다. 다음으로 `tools_condition`이 도구 호출이 필요하다고 판단하여 `sql_db_list_tables` 도구를 호출합니다. tools 노드가 테이블 목록을 반환합니다 (예: `['artists', 'albums', 'tracks', 'customers', 'invoices']`). assistant 노드가 테이블 목록을 받아서 사용자에게 자연스러운 언어로 설명합니다. "데이터베이스에는 artists, albums, tracks, customers, invoices 등의 테이블이 있습니다"와 같이 응답합니다. 마지막으로 `tools_condition`이 더 이상 도구 호출이 필요 없다고 판단하여 END로 이동하여 종료합니다.

```python
print("질문 1 결과:")
print(result1["messages"][-1].content)
```

결과를 출력합니다. `result1["messages"][-1]`은 마지막 메시지, 즉 에이전트의 최종 응답을 의미합니다.

실행하면 다음과 같은 결과가 나옵니다:

```
질문 1 결과:
데이터베이스에는 다음과 같은 테이블들이 있습니다:
- artists: 아티스트 정보
- albums: 앨범 정보
- tracks: 트랙 정보
- customers: 고객 정보
- invoices: 주문 정보
```

```python
# 질문 2: 복잡한 비즈니스 질문
result2 = sql_agent.invoke({
    "messages": [
        HumanMessage(content="2024년에 가장 많이 팔린 앨범 상위 5개를 알려줘. 앨범 이름과 아티스트 이름, 판매량을 포함해서 알려줘")
    ]
})
```

두 번째 질문은 더 복잡합니다. 실제 비즈니스 시나리오에서는 이런 복합적인 질문이 자주 발생합니다. 에이전트는 다음과 같은 ReAct 루프를 거칩니다.

먼저 assistant 노드가 질문을 분석하고, "2024년 판매량", "앨범", "아티스트" 정보가 필요하다고 판단합니다. 데이터베이스 구조를 파악하기 위해 `sql_db_list_tables` 도구를 호출합니다. tools 노드가 테이블 목록을 반환하면, assistant 노드가 판매량 정보는 `invoices` 테이블에, 앨범 정보는 `albums` 테이블에, 아티스트 정보는 `artists` 테이블에 있을 것으로 추론합니다. 각 테이블의 스키마를 확인하기 위해 `sql_db_schema` 도구를 여러 번 호출합니다.

assistant 노드가 스키마를 분석하면, `invoices` 테이블에 `InvoiceDate`, `AlbumId` 필드가 있고, `albums` 테이블에 `AlbumId`, `Title`, `ArtistId` 필드가 있으며, `artists` 테이블에 `ArtistId`, `Name` 필드가 있다는 것을 파악합니다. 이제 JOIN을 사용하여 적절한 SQL 쿼리를 생성하고, `sql_db_query` 도구를 호출하여 쿼리를 실행합니다.

tools 노드가 쿼리 결과를 반환하면, assistant 노드가 결과를 받아서 자연스러운 언어로 설명합니다. "2024년에 가장 많이 팔린 앨범은..."과 같이 비즈니스 팀이 이해하기 쉬운 형태로 응답하고, 더 이상 도구 호출이 필요 없다고 판단하여 종료합니다.

만약 쿼리에 오류가 있다면 (예: 테이블 이름 오타, 필드 이름 오류), 에이전트는 에러 메시지를 받고 다시 assistant 노드로 돌아가서 쿼리를 수정한 후 다시 시도합니다. 이렇게 ReAct 루프를 통해 문제를 단계별로 해결합니다.

```python
print("\n질문 2 결과:")
print(result2["messages"][-1].content)
```

실행하면 다음과 같은 결과가 나옵니다:

```
질문 2 결과:
2024년에 가장 많이 팔린 앨범 상위 5개는 다음과 같습니다:
```

이렇게 SQL 에이전트를 사용하면, 비즈니스 팀이 SQL을 몰라도 자연어로 데이터베이스를 조회할 수 있습니다.

SQL 에이전트의 실행 흐름을 정리하면 START에서 assistant로 시작하여, `tools_condition`을 통해 tools로 이동하고, 다시 assistant로 돌아오는 루프를 반복 실행한 후 END로 종료합니다. assistant는 추론 및 도구 호출 판단을 하고, tools는 SQL 도구를 실행합니다. 도구 결과를 보고 다시 추론하여 다음 단계를 결정하고, 도구 호출이 더 이상 필요 없을 때 종료합니다. 이렇게 ReAct 패턴을 사용하면 에이전트가 복잡한 SQL 질문을 단계별로 분해하여 해결할 수 있습니다.

SQL 에이전트는 테이블 목록 조회, 스키마 조회, 쿼리 실행 등의 도구를 사용합니다. LangGraph의 StateGraph로 에이전트를 구성하고, ReAct 패턴을 통해 assistant → tools → assistant 루프로 단계별로 문제를 해결합니다. 시스템 메시지로 에이전트의 동작 방식을 정의하고, 쿼리 실패 시 자동으로 루프를 통해 재시도합니다. 보안을 위해 읽기 전용 권한을 사용하고 SELECT 쿼리만 허용하며, 시스템 메시지에 이를 명시해야 합니다.

LangGraph를 사용하면 그래프 구조로 실행 흐름을 명확하게 제어할 수 있고, 각 노드의 입력/출력을 추적하기 쉬워 디버깅이 용이합니다. 필요에 따라 노드를 추가하거나 수정하기도 쉽고, MessagesState를 통해 대화 히스토리를 자동으로 관리할 수 있습니다.

이제 LangGraph를 사용하여 SQL 에이전트를 구축하는 방법을 배웠습니다. 다음 페이지에서는 이러한 에이전트를 로컬에서 실행하는 방법을 학습합니다.
